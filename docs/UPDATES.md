# Обновление MGate

`scripts/update.sh` обновляет стандартную установку Docker Compose: файлы релиза, образы,
миграции и скрипты. Работает в Community и Pro. Во время копирования базы и перезапуска
панель и почта временно недоступны. Постоянные тома и очередь не удаляются.

## Командная строка

Для первого и последующих обновлений выполните на сервере одну команду:

```sh
curl -fsSL https://raw.githubusercontent.com/mgate-server/mgate/main/scripts/update.sh | sudo bash -s -- --yes
```

Команда сама определяет каталог работающего Compose-проекта `mgate`, загружает обновлятор
последнего опубликованного стабильного релиза во временный каталог, создаёт копию базы и
настроек и обновляет установку. На хостах с systemd после успеха подключаются обновления
из административной панели. Работает и на старых релизах без `scripts/update.sh`.
`--yes` подтверждает запуск обновления. Существующие проверки установки сохраняются.

При необходимости добавьте `--dir /srv/mgate` или `--version YYYY.M.N` после `--yes`.
Уже установленный обновлятор также можно запускать локально:

```sh
cd /opt/mgate
./scripts/update.sh --check
sudo ./scripts/update.sh
sudo ./scripts/update.sh --version YYYY.M.N
sudo ./scripts/update.sh --yes       # явное подтверждение без терминала
sudo ./scripts/update.sh --status
```

Эквиваленты: `make update-check`, `sudo make update`, `sudo make update VERSION=YYYY.M.N`.
Другой каталог установки: `--dir /srv/mgate`. Поддерживаются опубликованные стабильные релизы;
повтор текущей версии ничего не меняет, понижение запрещено.

Нужны Python 3.10+, root, локальный Docker с Compose и доступ к GitHub, GHCR и Docker Hub.
Каталог установки, файлы и родительские каталоги должны принадлежать root без права записи
группы и остальных пользователей. Символические ссылки не поддерживаются.
Локальные изменения распространяемых файлов, конфликты новых файлов, Compose overrides,
нестандартные образы/реестр и изменения PostgreSQL/Valkey, сетей или томов требуют ручной
процедуры из DEPLOYMENT.md. Перед обновлением необходимы минимум 5 GiB и двойной размер базы
для резервной копии; дополнительное место требуется для образов.

Значения `.env` сохраняются; меняется только `MGATE_VERSION`, недостающие параметры добавляются
из нового шаблона. Секреты и сети автоматически не пересоздаются. Пользовательские файлы вне
релиза остаются на месте. Автоматической очистки старых образов и копий нет.

## Административная панель

Новый установщик автоматически подключает службу на хостах с systemd. Ручное подключение:

```sh
cd /opt/mgate
sudo make updater-install
```

Служба `mgate-updater.service` работает на хосте от root, используя механизм из
`/usr/local/lib/mgate-updater`; каталог установки записан в `/etc/mgate-updater.json`.
API получает только Unix-сокет `.mgate-updater/run/control.sock`, смонтированный в
`/run/mgate-updater` read-only. Docker-сокет и файлы хоста контейнеру не передаются.
После успешного обновления обновляется установленный механизм и перезапускается служба.

Суперадминистратор открывает **Настройки сервера → Обновления**, проверяет версию,
читает описание релиза и подтверждает **Обновить**. Диалог фиксирует конкретную версию.
Операция продолжает работать при перезапуске API; панель автоматически восстанавливает
получение состояния. При потере ответа на запуск сначала проверьте состояние операции.

Без systemd доступен CLI. Helm и all-in-one используют прежние процедуры.
Для работы кнопки API должен быть запущен с новым Compose-файлом и подключённой службой.

### Первый переход со старого релиза

Если `update.sh` ещё нет, используйте ту же однострочную команду из раздела выше.
Она загружает механизм обновления отдельно от установки и после успешного перехода
подключает хостовую службу на серверах с systemd.

При ручном запуске из отдельно распакованного нового релиза также доступны команды:

```sh
sudo bash /path/to/new-release/scripts/update.sh --dir /opt/mgate --version YYYY.M.N
sudo bash /opt/mgate/scripts/update.sh --dir /opt/mgate --install-service
```

Не копируйте новые скрипты поверх прежнего релиза перед запуском: проверка локальных
изменений остановит обновление. Первый переход выполняется через CLI; в старом API ещё нет
эндпоинтов обновления. Следующие обновления доступны из панели.
Если прежний установщик сохранил групповые права записи из архива, перед первым переходом
администратор должен проверить владельцев и убрать запись группы/остальных пользователей
у файлов и каталогов установки. Проверка укажет конкретный небезопасный путь. Новый
установщик нормализует права распространяемых файлов независимо от umask.

## Копия и восстановление

Состояние: `.mgate-updater/state/job.json`. Копия: `.mgate-updater/state/backups/<id>/`:

- `database.dump` — PostgreSQL custom dump, проверенный через `pg_restore --list`.
- `.env` — прежние параметры и ключи расшифрования данных.
- `files/`, `manifest.json` — прежние файлы и перечень затрагиваемых путей.
- `complete.json` — признак успешно созданной и проверенной копии.

Без `complete.json` копия незавершена. Каталог состояния доступен только root и содержит
секреты; переносите копии в защищённое хранилище. Это копия базы и настроек, а не всего
почтового хранилища. Регулярный полный backup остаётся отдельной задачей — см. BACKUP.md.

До начала миграций при ошибке восстанавливаются файлы и запускаются прежние сервисы.
После начала миграций автоматического отката базы нет: `recovery_required` блокирует новый
запуск. После прерывания процесса состояние `interrupted` также требует проверки.
Если миграции завершились ошибкой, API остаётся остановленным: состояние смотрите через
`sudo ./scripts/update.sh --status` на хосте. Панель сможет получить результат после
восстановления API; сама потеря связи не означает успешное или неуспешное завершение.

Для восстановления остановите службу обновления и сервисы, пишущие данные. Сохраните
текущую базу и почтовые тома отдельно: новый стек мог успеть принять почту после копии.
По `backup_path` найдите завершённую копию. Верните `files/` и прежний `.env`; удаляйте
только добавленные новым релизом файлы из `manifest.json`, отсутствующие в `files/`.
Не удаляйте пользовательские файлы и тома. Если миграции начинались, восстановите дамп
через `pg_restore` в отдельную пустую базу, проверьте её и согласуйте новые письма до
переключения; подробности в BACKUP.md. Не запускайте старый backend поверх неизвестной схемы.

После восстановления проверьте вход, API, приём и доставку почты. Затем подтвердите:

```sh
sudo ./scripts/update.sh --acknowledge-recovery
sudo systemctl start mgate-updater
```

Подтверждение только снимает блокировку и само не восстанавливает данные.
Диагностика: `systemctl status mgate-updater`, `journalctl -u mgate-updater`.

## API

`GET /api/v1/admin/updates` возвращает доступность службы, версии, ссылку на релиз и последнюю
операцию. `?refresh=true` обновляет метаданные принудительно; обычные запросы используют кеш
до пяти минут. Ошибка сети не скрывает состояние операции.

`POST /api/v1/admin/updates` принимает `{"version":"YYYY.M.N"}` и возвращает `202` с операцией.
Оба эндпоинта требуют SuperAdmin; cookie-запросы защищены CSRF. Инициатор фиксируется до
запуска в аудите `system.update.requested` и в состоянии на хосте. Конкурирующий запуск,
недоступная версия или необходимость восстановления возвращают `409`.
