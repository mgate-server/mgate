# Тестирование MGate

Каталог `tests/` содержит e2e-, нагрузочные- и deliverability-сценарии
(`tests/e2e/`, `tests/load/`, `tests/deliverability/`) — владелец
конкретных сценариев и раннеров определяется тем, чья функциональность
тестируется; этот документ описывает методологию и уровни тестирования
**для этого репозитория** (deploy kit + почтовый стек + SPA), чтобы CI
(`ci.yml`) и релизный чек-лист опирались на одни и те же
критерии.

**Модульные и интеграционные тесты закрытого backend не описаны здесь и не
запускаются из этого репозитория** — его исходный код и тесты не
публикуются. Здесь backend всегда участвует как уже собранный
чёрный ящик (скачанный образ) — тестируется его наблюдаемое поведение
(API-ответы, доставка почты, health-чеки), а не внутренняя реализация.

## Установщик

`make test-installer` запускает изолированные регрессионные проверки
`scripts/install.sh`: загрузка релиза, генерация и сохранение `.env`, проверка доменов,
портов и подсетей, ожидание миграций и готовности сервисов. Команды установки и запуска контейнеров
подменяются; отдельно проверяется разбор конфигурации настоящим Compose и подключение домена
через локальный HTTPS-сервер. Проверки не устанавливают пакеты и не запускают почтовый стек.
В CI дополнительно проверяются синтаксис Bash и ShellCheck.

## Уровни тестирования

### Механизм обновления

`make test-updater` проверяет обновление без сети и запуска контейнеров: сохранение настроек,
копирование базы, отказ при локальных изменениях, блокировку параллельных операций, откат
до миграций, обработку прерываний и Unix-сокет службы.

`make test-updater-docker` использует отдельный Compose-проект со случайным именем без
публикации портов. Нужны заранее загруженные `postgres:18-alpine`, `python:3.12-slim-bookworm`
и `alpine:latest`. Почтовые сервисы в этом тесте заменены минимальными контейнерами;
проверяются настоящая миграция PostgreSQL, сохранность тестового письма и очереди в томах,
версия HTTP API и восстановление дампа в отдельную базу. После теста удаляются только
контейнеры и тома созданного проекта. Это дополнение к почтовым E2E-тестам.

### 1. Unit-тесты (только фронтенд)

`npm test` в `web/` (`make test-web`) — компонентные и утилитные тесты
SPA (Vitest). Быстрые (секунды), запускаются на каждый PR. Проверки
скриптов развёртывания описаны выше в разделе «Установщик».

### 2. Интеграционные тесты

Тесты, требующие реальной инфраструктуры, но не полного стека контейнеров
почтовых демонов:
- Postfix/Dovecot/Rspamd/unbound конфигурация — через
  `make validate-configs` (реальные `postfix check`, `doveconf -n`,
  `rspamadm configtest`, `unbound-checkconf`, см. `ci.yml` → job
  `validate-configs`) — проверяет реальный бинарник демона на реальном
  конфиге, но не поднимает сеть между сервисами.
- `make compose-config` — рендерит и валидирует все варианты compose
  (base/build/dev, все профили) без запуска контейнеров.
- Интеграционные тесты самого backend (БД-репозитории против живого
  PostgreSQL и т.п.) — выполняются вендором в собственном закрытом конвейере и
  отсюда не запускаются.

### 3. E2E-дымовой тест (smoke)

`make smoke` → `scripts/smoke-test.sh` — поднимает стек (или использует уже
поднятый через `make up`/`make dev`) и прогоняет минимальный сквозной
сценарий (текущая реализация провижинит тестовые данные напрямую в БД; переход
на публичный admin API — в планах):
1. `GET /api/v1/system/health` и `GET /api/v1/mail/health` → `200 {"status":"ok"}`.
2. Создать тестовый домен + ящик напрямую через `psql` (идемпотентно),
   хэш пароля — `doveadm pw -s ARGON2ID` (тот же формат PHC-строки, что
   проверяет бэкенд при логине), публикация тестового DKIM-ключа в Valkey db1
   (`HSET DKIM_KEYS`/`DKIM_SELECTORS`).
3. Отправить письмо на этот ящик через `postfix` (SMTP на порту из
   `MGATE_SMTP_PORT`, по умолчанию `127.0.0.1:25`; на rootless Docker порт
   переопределяется этой же переменной) — отправитель
   должен быть в тестовом домене (не `example.com`: IANA-домены публикуют
   null MX и отклоняются `reject_unknown_sender_domain`).
4. Проверить, что письмо доставилось (LMTP → Dovecot Maildir) и видно по
   IMAP (STARTTLS-логин на `MGATE_IMAP_PORT`). Письмо от домена без
   SPF/DKIM/DMARC ожидаемо получает высокий Rspamd-score (пример: 8.00/15
   с включённым `add_header`) и попадает не в INBOX, а в Junk через
   `sieve_before` — это ожидаемое поведение антиспама, тест принимает
   доставку в любую из двух папок и сообщает, в какую именно.
5. Проверить, что DKIM-подпись присутствует и валидна (Rspamd лог/заголовок
   `Authentication-Results` на входящем тестовом письме от самого себя —
   либо сторонний relay/mailpit).

Более широкий e2e-набор (`tests/e2e/`) — сценарии по каждой функциональной
области (домены, алиасы, списки рассылки, 2FA, автоответчик, Sieve-фильтры,
лицензирование) добавляются по мере реализации соответствующей
функциональности; покрытие отслеживается в [`ROADMAP.md`](ROADMAP.md).

### Известная ловушка: домен для smoke-теста

По умолчанию `scripts/smoke-test.sh` берёт домен из `MGATE_HOSTNAME` (например,
`mail.example.com` → `example.com`). Домены IANA из зоны `example.*` публикуют жёсткие политики
`SPF -all` и `DMARC p=reject`, поэтому входящее письмо такого теста будет корректно отвергнуто
почтовым фильтром — это правильное поведение сервера, а не сбой стенда. Задавайте свой домен
явно:

```bash
make smoke SMOKE_TEST_DOMAIN=mgate.test
```

## Нагрузочное тестирование (методология: 50 сообщений/с)

Целевой показатель продукта: **до 50 сообщений/с на 4 vCPU /
8 GB RAM**. Методология (`tests/load/`; скрипты `api_load.py` и `smtp_load.py`
используют только стандартную библиотеку Python; для SMTP-нагрузки также
подходят `smtp-source`/`smtp-sink` из пакета Postfix — они уже есть в образе
`docker/postfix`):

1. **Профиль нагрузки**: постоянный поток входящих SMTP-сессий,
   параллелизм подобранный так, чтобы держать целевые 50 msg/s в течение
   как минимум 10 минут (не только пиковый всплеск) — сообщения разного
   размера (мелкие текстовые + доля с вложениями до `MGATE_MESSAGE_SIZE_LIMIT`),
   на несколько разных тестовых доменов/ящиков (не все в одну очередь) и
   на разные `postfix`/`dovecot`/`rspamd` пути реалистично.
2. **Метрики, которые снимаются во время теста**: `/metrics` (латентность
   API, глубина очереди `jobs`), размер очереди Postfix (`postqueue -j` /
   `mgate-agent GET /v1/queue`), CPU/RAM хоста или контейнеров (`docker
   stats`), латентность доставки "конец-в-конец" (время от инъекции письма
   до появления в Maildir/через IMAP).
3. **Критерий прохождения**: очередь Postfix не растёт неограниченно при
   целевой скорости (успевает разгребаться быстрее или наравне со
   входящим потоком), латентность API/webmail остаётся ≤ 200 мс (целевой
   целевой показатель для не-почтовых операций), ни один сервис не падает по
   OOM/креша в течение теста на референсной конфигурации (4 vCPU/8 GB,
   профиль `clamav` включён — самый тяжёлый случай).
4. Результаты фиксируются в отчёте о релизе с указанием точной
   версии/коммита, конфигурации (профили, ресурсы), инструмента и сырых
   цифр — не только "прошло/не прошло".

## Чек-лист доставляемости 10/10 (mail-tester.com)

Перед каждым релизом и после существенных изменений в
Postfix/Rspamd/DKIM-конфигурации — прогнать тестовую инсталляцию через
[mail-tester.com](https://www.mail-tester.com/) (или аналог) и добиться
максимальной оценки. Пункты, которые типично проверяет такой сервис и
которые должны быть закрыты конфигурацией MGate:

- [ ] SPF настроен и проходит (`v=spf1 mx -all` или эквивалент — см.
      `docs/DNS.md` §4).
- [ ] DKIM настроен, подпись валидна, используется актуальный (не
      скомпрометированный/не слишком короткий) ключ — минимум 2048 бит.
- [ ] DMARC настроен, в идеале на `p=quarantine`/`p=reject` для боевого
      домена (после периода `p=none`, см. `docs/DNS.md` §6) —
      тестовый прогон допустим и на `p=none`, но итоговая рекомендация
      для продакшена — не оставаться там навсегда.
- [ ] PTR (reverse DNS) корректно резолвится на `MGATE_HOSTNAME`.
- [ ] HELO/EHLO совпадает с PTR/A-записью сервера.
- [ ] Сервер не находится ни в одном из проверяемых DNSBL/чёрных списков.
- [ ] TLS доступен на подключении (STARTTLS на 25/587, либо wrapper TLS на
      465) с современным набором шифров (опция Traefik `modern` для веб-хостов;
      SMTP:25 остаётся opportunistic TLS 1.2+).
- [ ] Содержимое письма проходит базовые эвристики спам-фильтров
      (соотношение текст/HTML, отсутствие сломанной разметки, корректные
      заголовки `Message-ID`/`Date`/`From`) — для тестовых писем,
      сгенерированных самим MGate (уведомления, восстановление пароля).
- [ ] Итоговая оценка **10/10** (или максимум, который даёт выбранный
      сервис) фиксируется скриншотом/отчётом в материалах релиза.

Автоматизация части этого чек-листа (`tests/deliverability/`) частично
реализована (`verify_dns_syntax.py` проверяет синтаксис SPF/DKIM/DMARC-записей).
Полная проверка — скрипт, который поднимает эталонную конфигурацию, отправляет
тестовое письмо через публичный relay/second instance и проверяет
`Authentication-Results` заголовки программно (SPF/DKIM/DMARC pass) без
привязки к конкретному внешнему сервису, — пока не написана; ручной прогон через
mail-tester.com остаётся финальным подтверждением перед релизом, так как
он видит инсталляцию так же, как реальный получатель.

## Тесты безопасности

- **Статический анализ зависимостей (этот репозиторий)**: `npm audit` для
  `web/` (в CI — информационный, `continue-on-error`; перевод в блокирующий
  режим запланирован после стабилизации дерева зависимостей), `hadolint` для
  всех `docker/*/Dockerfile`. Проверка зависимостей backend выполняется
  вендором в собственном конвейере и отсюда не запускается.
- **Секреты**: ни один тест/CI-джоб не должен печатать значения
  `MGATE_INTERNAL_TOKEN`, `DOVEADM_API_KEY`, `RSPAMD_CONTROLLER_PASSWORD`,
  `MGATE_SECRET_KEY`, паролей — проверяйте вывод шагов `compose-config`/
  `validate-configs` перед тем, как включать его в артефакты CI.
- **Границы `/internal/v1/*`**: регресс-тест (`tests/e2e/`, пока не
  написан) должен подтверждать, что порт `8081` (`api`) и control-порты
  `mgate-agent` (`7070`) недостижимы с сети `public`/снаружи — то есть что
  Traefik физически не имеет маршрута туда (не полагаться только на
  `Authorization: Bearer` — отсутствие сетевого пути является первым
  рубежом обороны, см. [`ARCHITECTURE.md`](ARCHITECTURE.md)).
- **Аутентификация, лицензирование и другая логика внутри закрытого
  backend** (Argon2id, TOTP, rate-limit, проверка лицензии и т.д.):
  покрываются тестами самого backend у вендора — не тестируются и не могут
  тестироваться из этого репозитория, так как код здесь не публикуется.
  Этот репозиторий может только тестировать *наблюдаемое поведение* через
  публичный API (e2e), не внутреннюю реализацию.
- **Внешний security-аудит**: независимая проверка
  (или как минимум структурированный self-audit по OWASP ASVS/чек-листу
  для почтовых серверов) поверх модели угроз в `docs/SECURITY.md`.

## CI-эквивалентность

Каждый job в `.github/workflows/ci.yml` соответствует одной или нескольким
целям `make` (список — `make help`) — если вы добавляете новый
вид проверки, добавьте одновременно: (1) цель `make`, (2) job/шаг в
`ci.yml`, (3) строку в этом документе с методологией. Раздельные "CI
запускает X, а `make` умеет только Y" со временем расходятся и ломают
доверие к зелёному CI как индикатору "у меня локально тоже пройдёт".

Публикация образов и релизов в CI **не выполняется**: образы собирает и
публикует вендор своим релизным конвейером, поэтому в `.github/workflows/`
остаётся только `ci.yml` (линт, тесты, сборка и валидация конфигураций).
