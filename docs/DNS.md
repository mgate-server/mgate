# DNS-записи для домена MGate

Мастер добавления домена в админке (и CLI `mgate dns records <domain>`,
реализация — внутри закрытого бэкенда) генерирует набор рекомендуемых DNS-записей
для каждого домена, добавленного в MGate. Этот документ описывает каждую
запись, зачем она нужна, и даёт пример для домена **`example.com`**,
почтового сервера с именем **`mail.example.com`** (значение
`MGATE_HOSTNAME`) и IP-адресом **`203.0.113.10`** (пример из диапазона
TEST-NET-3, RFC 5737 — замените на настоящий IP вашего сервера).

Часть записей (`MX`, `A`/`AAAA` почтового сервера, `SPF`, `DKIM`, `DMARC`)
обязательна для доставляемости; остальные (`MTA-STS`/`TLS-RPT`,
autoconfig/autodiscover) — рекомендуются, но опциональны, и мастер помечает
их соответственно. `BIMI` и `DANE TLSA` мастер не создаёт — они описаны
ниже как ручные опциональные шаги.

## 1. MX — куда доставлять почту для домена

```
example.com.        IN MX  10 mail.example.com.
```
Один MX на `MGATE_HOSTNAME`, приоритет `10` (значение не критично при одном
сервере). Если у вас несколько доменов на одной инсталляции MGate, MX
каждого домена указывает на тот же `mail.example.com`.

## 2. A / AAAA — адрес самого почтового сервера

```
mail.example.com.   IN A     203.0.113.10
mail.example.com.   IN AAAA  2001:db8::10        ; если есть IPv6
```
Обязательно должна существовать A/AAAA-запись именно для имени из MX
(`mail.example.com`), а не только для голого `example.com`.

## 3. PTR — обратная зона (настраивается НЕ здесь)

```
10.113.0.203.in-addr.arpa.  IN PTR  mail.example.com.
```
PTR-запись создаётся не в вашей DNS-зоне, а в reverse-зоне, которой
управляет провайдер сервера (хостинг/облако) — обычно через панель
управления VPS/выделенным сервером. Мастер DNS показывает, какое значение
должно быть в PTR, и умеет проверить его (обратный
DNS-запрос), но не может создать его сам. См. также `docs/DEPLOYMENT.md` §1.

## 4. SPF — кто имеет право отправлять почту от имени домена

```
example.com.         IN TXT  "v=spf1 mx ~all"
```
`mx` разрешает отправку с серверов из MX-записей домена (то есть с
`mail.example.com`); `~all` — мягкий отказ (softfail) всем остальным: такие
письма принимаются, но помечаются как подозрительные. Когда убедитесь, что
все легитимные источники учтены, можно вручную заменить `~all` на `-all`
(жёсткий отказ). Если у домена есть дополнительные легитимные отправители
(например, внешний ESP для транзакционных писем), добавьте их в запись
самостоятельно (`include:...`) — итоговая запись не должна превышать 10
DNS-lookup (лимит SPF, RFC 7208).

## 5. DKIM — криптографическая подпись писем

```
<selector>._domainkey.example.com.  IN TXT  "v=DKIM1; k=rsa; p=<public-key-base64>"
```
- Ключ генерируется автоматически при создании домена: **RSA-2048**
  (другие размеры ключа не поддерживаются). Значение длиннее 255 байт, поэтому
  при публикации его нужно разбить на несколько строк в кавычках в рамках
  одной TXT-записи (RFC 1035) — это поддерживают все современные
  DNS-серверы.
- `<selector>` — метка ключа; при создании домена используется `mgate`, при
  ротации — новый селектор вида `mg<ГГГГММДД><4 символа>`. **Ротация DKIM**
  выполняется вручную кнопкой «Ротировать DKIM» в админке: новый ключ
  становится активным сразу, а старый не удаляется из DNS автоматически —
  его запись должна оставаться опубликованной ещё некоторое время (пока не
  будут доставлены/проверены ранее подписанные сообщения — обычно
  рекомендуется 1–2 недели), прежде чем её можно удалить. Процедура —
  `docs/OPERATIONS.md` § «Ротация DKIM»; автоматической плановой ротации
  нет.
- Приватный ключ хранится зашифрованным (см. `MGATE_SECRET_KEY`) и
  публикуется в Valkey для Rspamd (хэши `DKIM_KEYS`,
  `DKIM_SELECTORS`, см. `docs/mail/rspamd.md`), не пишется на диск в открытом виде.

## 6. DMARC — политика для получателей и отчётность

```
_dmarc.example.com.  IN TXT  "v=DMARC1; p=none; rua=mailto:dmarc-reports@example.com; fo=1"
```
**Рекомендуемый план внедрения** (мастер изначально предлагает `p=none`;
ужесточать политику нужно вручную, изменив запись в DNS — автоматически она
не переключается, а вкладка DMARC домена показывает, готов ли домен к
следующему шагу):

1. `p=none` — только сбор отчётов (`rua`), почта не блокируется ни при
   каком исходе SPF/DKIM. Оставайтесь на этом шаге минимум 1–2 недели и
   проверьте отчёты (агрегированные `rua`, при необходимости `ruf` для
   форензики) — убедитесь, что все ваши легитимные источники почты
   проходят SPF/DKIM/выравнивание (alignment).
2. `p=quarantine` — письма, не прошедшие проверку, помечаются как спам
   (складываются в папку "Спам" получателя), но не отклоняются полностью.
3. `p=reject` — письма, не прошедшие проверку, отклоняются на уровне SMTP
   получателя. Переходите на этот шаг только после уверенности, что отчёты
   больше не показывают ложных срабатываний от легитимных источников.

Отчёты `rua` приходят на указанный адрес в виде XML: их нужно загружать в
MGate **вручную** (вкладка DMARC домена → загрузка XML-отчёта) — автоматического
приёма и разбора отчётов нет. По загруженным отчётам строится сводка; полные
IP-адреса источников, история до 90 дней и скачивание исходных XML — функции
Pro-модуля DMARC Intelligence (входит в любую Pro-лицензию; имена хостов и география источников не
определяются).

Дополнительно: `pct=<N>` можно использовать для постепенного наката
(применять политику только к N% писем) на переходе между шагами 2 и 3 у
доменов с большим объёмом почты.

## 7. MTA-STS и TLS-RPT — принудительный TLS для входящей почты

MTA-STS требует одновременно DNS-запись и файл политики, отдаваемый по
HTTPS на специальном поддомене:

```
_mta-sts.example.com.  IN TXT  "v=STSv1; id=2026091201"
mta-sts.example.com.   IN A    203.0.113.10        ; тот же сервер, HTTPS обязателен
```
Traefik маршрутизирует `HostRegexp(^(autoconfig|autodiscover|mta-sts)\..+$)`
на `api:8080` (см. `docs/ARCHITECTURE.md` §3), который отдаёт файл политики по
`https://mta-sts.example.com/.well-known/mta-sts.txt`:
```
version: STSv1
mode: testing
mx: mail.example.com
max_age: 86400
```
Сейчас MGate отдаёт политику в режиме `testing` (отправители лишь сообщают о
проблемах TLS через TLS-RPT, но не отказывают в доставке); переключение в
`enforce` в этой версии недоступно. Политика публикуется для входящей почты;
принудительная проверка TLS при отправке исходящей почты на чужие домены
(outbound MTA-STS) в этой версии не выполняется. `id` в TXT-записи — произвольная строка, увеличивайте/меняйте её при каждом
изменении файла политики, чтобы кэширующие получатели перечитали его.

TLS-RPT (отчёты об ошибках TLS-подключения от получателей):
```
_smtp._tls.example.com.  IN TXT  "v=TLSRPTv1; rua=mailto:tlsrpt-reports@example.com"
```

## 8. Autoconfig / Autodiscover / SRV (RFC 6186) — автонастройка почтовых клиентов

Чтобы Thunderbird, Outlook, почтовые приложения на телефонах могли
настроиться сами по домену email-адреса:

```
autoconfig.example.com.    IN CNAME  mail.example.com.
autodiscover.example.com.  IN CNAME  mail.example.com.

_submission._tcp.example.com.  IN SRV  0 1 587 mail.example.com.
_imaps._tcp.example.com.       IN SRV  0 1 993 mail.example.com.
_pop3s._tcp.example.com.       IN SRV  0 1 995 mail.example.com.   ; если POP3 включён
```
`autoconfig.*`/`autodiscover.*` также маршрутизируются Traefik на `api:8080`
через тот же `HostRegexp`, который отдаёт Mozilla-формат autoconfig XML
(`/.well-known/autoconfig/mail/config-v1.1.xml`) и отвечает на Microsoft
Autodiscover POST-запросы. SRV-записи (RFC 6186) — декларативный способ
того же самого для клиентов, которые их поддерживают напрямую.

## 9. BIMI (опционально) — логотип бренда в письме у получателя

Мастер MGate эту запись не создаёт и не проверяет — при необходимости
добавьте её в зону вручную:

```
default._bimi.example.com.  IN TXT  "v=BIMI1; l=https://example.com/logo.svg;"
```
Требует: домен уже на `p=reject` (или как минимум `quarantine` с
достаточным `pct`) в DMARC, логотип в формате SVG Tiny PS, у крупных
провайдеров (Gmail, Yahoo) — дополнительно **VMC (Verified Mark
Certificate)**, платный сертификат у авторизованного удостоверяющего
центра, подтверждающий права на товарный знак. VMC MGate не выпускает и не
продаёт — это отдельная услуга у стороннего CA.

## 10. DANE TLSA (опционально) — привязка TLS-сертификата к DNS через DNSSEC

Мастер MGate TLSA-запись не создаёт, не вычисляет и не обновляет — её
публикация и обновление при смене сертификата полностью на вашей стороне:

```
_25._tcp.mail.example.com.  IN TLSA  3 1 1 <sha256-hash-of-spki>
```
Требует, чтобы зона `example.com` была подписана **DNSSEC** — без DNSSEC
TLSA-запись не даёт защиты (её можно подделать так же, как остальной DNS) и
некоторые проверяющие MTA будут её игнорировать или, в строгом режиме,
считать ошибкой конфигурации. Включайте DANE только если ваш DNS-провайдер и
регистратор домена поддерживают DNSSEC end-to-end, и помните: устаревший
хэш после смены сертификата приведёт к отказам в доставке.

## Проверка записей

`mgate dns records <domain>` печатает ожидаемые значения; проверка
фактического состояния DNS (что резолвится прямо сейчас) выполняется бэкендом
**по запросу** — кнопкой «Проверить DNS» в мастере админки на странице
домена. Фоновой периодической проверки с предупреждением нет: после
изменения записей (ротация DKIM, смена IP сервера, переезд DNS) запускайте
проверку вручную.

## Автоматическая публикация записей (DNS-Автопилот)

Вместо копирования записей вручную мастер домена умеет синхронизировать их
через API DNS-провайдера кнопкой «Автонастройка». Поддерживаются только
**Cloudflare** и **Selectel** (нужен API-токен провайдера с правом
редактирования зоны, он передаётся при каждом запуске). Разовая «Автонастройка»
доступна во всех редакциях. Автоматическая фоновая сверка записей (Pro-модуль
`pro.dns_autopilot`) **в разработке** и в этой версии не работает.
