# Эксплуатация MGate

## Управление очередью писем

Очередь Postfix управляется через **`mgate-agent`** control API (порт
`7070`, backend-only, см. [`ARCHITECTURE.md`](ARCHITECTURE.md)), которое
оборачивает `postqueue`/`postsuper` и выставляется в админку через backend
(`api`):

| Действие | mgate-agent | Соответствие в админке |
|---|---|---|
| Просмотр очереди | `GET /v1/queue` (`postqueue -j`, JSON per-message) | Раздел «Очередь» |
| Принудительная обработка всей очереди | `POST /v1/queue/flush` | Кнопка «Flush» |
| Удержать письмо | `POST /v1/queue/{id}/hold` | Действие в строке письма |
| Снять с удержания | `POST /v1/queue/{id}/release` | Действие в строке письма |
| Поставить в очередь заново (requeue) | `POST /v1/queue/{id}/requeue` | Действие в строке письма |
| Удалить письмо из очереди | `DELETE /v1/queue/{id}` | Действие в строке письма |

CLI-альтернатива при доступе по SSH: `docker compose exec postfix postqueue
-p` (просмотр), `docker compose exec postfix postsuper -d ALL` (очистить
всё — использовать с осторожностью). Предпочитайте control API/админку —
она пишет действие в `audit_log`.

## Логи

- **Live Logs** в админке — построены на потоке `mgate-agent` → Valkey
  stream `mgate:logs` (`XADD ... MAXLEN ~ 200000`) → `worker`
  (consumer group `ingest`) → БД (`mail_events`, партиционирована) → API
  отдаёт с фильтрацией по IP/адресу/статусу и живым обновлением (WS/SSE).
- **Логи контейнеров** напрямую: `make logs` (все сервисы) или `docker
  compose logs -f <service>`. Формат JSON (`json-file`, ротация
  `max-size=10m, max-file=5`) — удобно
  перенаправлять во внешний коллектор (Loki, Vector, etc.) через
  `docker logs` или монтированием `/var/lib/docker/containers/*/*.log`,
  если это соответствует вашей инфраструктуре логирования.
- **Rspamd**: собственный лог + `metadata_exporter` → `POST
  http://api:8081/internal/v1/events/rspamd` (те же `mail_events`).
- **Dovecot**: `mgate-agent` (роль `dovecot`) читает `/dev/log`, эхо в
  stdout + тот же `mgate:logs` stream; аутентификации дополнительно видны
  через `POST /internal/v1/events/dovecot`.

## Статистика

Почасовые срезы (`stats_hourly`, заполняется `worker` job "stats
rollups" из `mail_events`) — входящий/исходящий трафик, спам,
доставлено/отклонено, по доменам и по ящикам. Раздел «Статистика» в
админке строит графики поверх этой таблицы. `GET /metrics` (Prometheus
text format, порт `8081`, backend-only) — для внешнего мониторинга (см.
ниже).

## Сертификаты: загрузка и замена

**Автоматический выпуск и продление (Let's Encrypt / ZeroSSL) — в разработке, в этой версии не
работает.** По умолчанию сервер использует самоподписанный сертификат, поэтому для рабочей
эксплуатации загрузите собственный сертификат и **продлевайте его вручную**.

- **Загрузка**: админка → «Сертификаты» → «Загрузить сертификат» (цепочка PEM — сертификат
  сервера первым — и незашифрованный закрытый ключ PEM). Сервер проверяет цепочку, срок
  действия и соответствие ключа; ключ хранится в БД в зашифрованном виде.
- **Продление**: загрузите новый сертификат под тем же именем — он заменит прежний. Кнопки
  «Продлить сейчас» нет: она относилась к автоматическому выпуску. Дата окончания видна в списке
  «Сертификаты» (за 14 дней до окончания дата подсвечивается) — поставьте себе напоминание
  заранее.
- **Ошибки**: если сертификат не принят, админка показывает причину (например, ключ не
  подходит к сертификату, сертификат истёк, не покрыто запрошенное имя).
- После записи нового сертификата в `/certs/live/<name>/` или
  `/certs/default/` — `mgate-agent` (файловый watcher на `notify`)
  автоматически выполняет `postfix reload`/`doveconf reload` в
  соответствующих контейнерах; Traefik подхватывает
  `/etc/traefik/dynamic/10-certs.yml` без перезапуска (динамическая
  конфигурация).

## Ротация DKIM

Ротация выполняется вручную, по инициативе администратора. Ключи всегда RSA-2048.

1. В админке откройте домен → вкладка DNS → кнопка «Ротировать DKIM». Сервер
   генерирует новый ключ RSA-2048 с новым селектором (вида
   `mg<ГГГГММДД><4 символа>`), сохраняет его, публикует в Valkey для Rspamd и
   **сразу делает активным** — новая исходящая почта подписывается им с этого
   момента. Предыдущий ключ деактивируется (но остаётся в базе).
2. **Немедленно** опубликуйте новую TXT-запись `<selector>._domainkey.<domain>`
   (значение показывает мастер DNS; см. [`DNS.md`](DNS.md) §5) — пока она не
   распространилась, получатели не смогут проверить новую подпись. Поэтому
   ротацию лучше делать в период низкой нагрузки; учитывайте TTL записи.
3. **Не удаляйте старую TXT-запись сразу** — оставьте её опубликованной ещё
   1–2 недели (пока не будут доставлены ранее подписанные письма и пока
   получатели не перестанут проверять письма по старой подписи); затем
   удалите её из DNS.

Автоматическая плановая ротация с напоминанием пока не реализована.

## Обновления

См. [`DEPLOYMENT.md`](DEPLOYMENT.md#5-обновления-и-пиннинг-версий): версии
CalVer (`YYYY.M.N`), пиннинг `MGATE_VERSION`, обновление через `docker
compose pull && docker compose up -d` (миграции применяются автоматически) и
откат. Перед обновлением прочитайте [`CHANGELOG.md`](../CHANGELOG.md) и
заметки релиза в [GitHub Releases](https://github.com/mgate-server/mgate/releases)
(вендор публикует их вместе с каждой версией) на предмет несовместимых
изменений и сделайте бэкап ([`BACKUP.md`](BACKUP.md)).

## Масштабирование

Одноузловой старт — один сервер, все сервисы через `docker-compose.yml`.
Пути масштабирования по мере роста инфраструктуры (см. также [`docs/DEPLOYMENT.md`](DEPLOYMENT.md) §8, [`docs/ROADMAP.md`](ROADMAP.md) и подробный регламент отказоустойчивости [`docs/HA.md`](HA.md)):
- **Вертикально** — увеличение vCPU/RAM хоста (`postgres`, `valkey`, `rspamd` и `clamav` первыми упираются в ресурсы при росте потока почты).
- **Горизонтально в Kubernetes через Helm** ([`deploy/helm/mgate/`](../deploy/helm/mgate/)) — независимое масштабирование stateless-реплик (`api`, `webmail`, `web`, `worker`, `rspamd`) за общим Ingress-контроллером, StatefulSet для `postfix`/`dovecot` с общим хранилищем `vmail` на распределённой ФС (NFS v4, JuiceFS).
- **Вынос БД и кэша** — внешний управляемый кластер PostgreSQL (Patroni, CloudNativePG, AWS RDS Multi-AZ) и внешний Valkey/Redis с **одной точкой подключения** (Redis Cluster и Sentinel не поддерживаются).
- **Отказоустойчивость и кластеризация**: детальный анализ сценариев отказа (потеря узла Postfix, переключение Dovecot по схеме active/passive — один Dovecot на хранилище `vmail`, защита от split-brain сетевого хранилища) и параметров монтирования ФС документирован в [`docs/HA.md`](HA.md).
- Лимит Community-редакции — 1 домен; он снимается переходом на редакцию Pro — активацией лицензии ([`docs/LICENSING.md`](LICENSING.md)).

### Ориентиры по ёмкости

Целевые показатели: ≥ 50 писем/с и p95 ≤ 200 мс на 4 vCPU / 8 GB (методология нагрузочных
тестов — [`TESTING.md`](TESTING.md)). Ориентиры ниже — расчётные, а не гарантированные значения;
реальная пропускная способность зависит от оборудования, профиля почты и настроек антиспама и
антивируса. Проверьте её на своей инсталляции (`tests/load/`).

| Профиль инсталляции | Ресурсы (vCPU / RAM) | Ориентир по нагрузке |
|---|---|---|
| **Минимальный** | 2 vCPU / 4 GB | до 100 ящиков |
| **Референсный** | **4 vCPU / 8 GB** | **до 1 000 ящиков**, целевая пропускная способность ≥ 50 писем/с |
| **Производительный** | 8 vCPU / 16 GB | до 10 000 ящиков |
| **Кластерный (Helm)** | 16+ vCPU / 32+ GB | 50 000+ ящиков, горизонтальное масштабирование |

## Мониторинг (`/metrics`) и Observability

`GET http://api:8081/metrics` (Prometheus text exposition format,
backend-only — **не публикуется через Traefik**; порт `8081` нельзя
выставлять наружу) отдаёт метрики `api`/`worker`: HTTP-латентность и
коды ответов, размер очередей БД-джобов (`jobs` таблица, SKIP LOCKED),
статус фоновых задач (лицензия/log-ingest), количество
активных сессий. Dovecot дополнительно отдаёт собственные метрики на
`9900` (`openmetrics`, backend-only).

### Готовые шаблоны мониторинга
- **Правила алертов Prometheus**: [`deploy/prometheus/alerts.yaml`](../deploy/prometheus/alerts.yaml) — мониторинг доступности API/Dovecot, глубины очереди Postfix (>500 писем), всплесков подбора паролей, скорого истечения TLS-сертификатов (<14 дней), сбоев бэкапов и нехватки места на диске (<15%).
- **Дашборд Grafana**: [`deploy/grafana/dashboards/mgate-overview.json`](../deploy/grafana/dashboards/mgate-overview.json) — визуализация глубины очередей, сессий Dovecot, времени жизни сертификатов, динамики авторизаций (Success/Fail) и HTTP-трафика.
- **Проверка бэкапов**: `./scripts/verify-backup.sh [SNAPSHOT_ID]` (или `make verify-backup`) — автоматическая проверка целостности репозитория Restic и валидности дампа PostgreSQL через `pg_restore --list`.

## Типовые инциденты

### IP сервера попал в чёрный список (blacklisted)

1. Проверьте статус на нескольких DNSBL (`mxtoolbox.com/blacklists.aspx`
   или аналог) — какой конкретно список заблокировал IP.
2. Устраните причину: чаще всего — компрометация ящика (спам-рассылка через
   взломанные учётные данные) или неверная DKIM/SPF-конфигурация,
   заставившая легитимную почту выглядеть подозрительно. Проверьте Live
   Logs/статистику на аномальный всплеск исходящей почты по конкретному
   ящику — при необходимости смените пароль ящика (двухфакторная аутентификация пока в разработке и недоступна; для почтовых клиентов используйте пароли приложений).
3. Подайте заявку на делистинг через форму соответствующего DNSBL (у
   каждого — своя процедура и SLA, от минут до нескольких дней).
4. Профилактика: rate limits на ящик/домен/IP (политики в backend, счётчики в Valkey) уже
   ограничивают объём исходящей почты по умолчанию — проверьте, что лимиты
   не были ослаблены вручную.

### Браузер или почтовый клиент ругается на сертификат

Это ожидаемо, пока не загружен собственный сертификат: по умолчанию отдаётся самоподписанный
(автоматический выпуск Let's Encrypt — в разработке).

1. Проверьте раздел «Сертификаты» в админке: какой сертификат активен, не истёк ли он (статус
   «Истёк» / «Ошибка», текст ошибки показан под статусом).
2. Убедитесь, что сертификат покрывает `MGATE_HOSTNAME` (имя в SAN) и что цепочка загружена
   целиком: сертификат сервера, затем промежуточные.
3. Если загрузка отклонена, причина показывается в окне загрузки: ключ не соответствует
   сертификату, ключ зашифрован паролем (поддерживается только незашифрованный PEM),
   сертификат истёк или не покрывает запрошенные имена.
4. После замены сертификата Postfix/Dovecot/Traefik подхватывают его автоматически, обычно в
   течение минуты.

### Диск заполнен (disk full)

1. Проверьте, что именно растёт: `docker system df -v`, размер volumes
   `pg-data`/`vmail`/`rspamd-data`/`backups`. Частые причины: разросшаяся
   очередь Postfix из-за проблем с доставкой (см. «Управление очередью»
   выше), большие почтовые ящики без квот, накопленные старые бэкапы при
   некорректной ретеншн-политике restic.
2. Освободите место: `make backup` не поможет само по себе — сначала
   разберитесь с причиной. `docker system prune` (осторожно — не удаляет
   именованные volumes, но чистит неиспользуемые образы/слои) может дать
   быстрое временное облегчение при заполнении диска образами после
   многих обновлений.
3. Профилактика: настройте квоты на ящики (раздел «Ящики» в админке,
   Dovecot `quota`-плагин), мониторьте `/metrics`/место на диске отдельным
   алертом на уровне хоста (вне MGate — например, стандартный мониторинг
   вашего хостинг-провайдера или Prometheus node_exporter).

### ClamAV падает по памяти (OOM)

1. ClamAV (профиль `clamav`) — самый прожорливый по RAM сервис из-за базы
   сигнатур, загружаемой в память (freshclam обновления могут временно
   увеличивать потребление вдвое во время подгрузки новой базы). При
   `mem_limit`, заданном в compose, OOM внутри контейнера может привести к перезапуску clamd —
   проверьте `docker compose logs clamav` и `dmesg`/`docker inspect` на
   признаки OOM-killer.
2. Если сервер соответствует минимальным (не рекомендованным) 2 GB RAM —
   ClamAV, скорее всего, не влезает стабильно; либо увеличьте RAM сервера
   до рекомендованных 4 vCPU/8 GB (см. `README.md`), либо отключите
   антивирус (уберите `clamav` из `COMPOSE_PROFILES`) — это осознанный
   компромисс — минимальная конфигурация для бесплатного почтового сервера.
3. Если RAM достаточно, но OOM всё равно происходит — проверьте, не
   задан ли `mem_limit` слишком консервативно относительно актуального
   размера базы сигнатур ClamAV (база растёт со временем) и скорректируйте
   его в вашем собственном compose-override.
