# Развёртывание MGate

## Способы поставки

1. **Docker Compose** (основной, описанный ниже) — один сервер, `docker
   compose up -d`.
2. **Helm chart** (`deploy/helm/mgate/`) — для Kubernetes; см. раздел
   [Helm](#6-helm-chart-kubernetes) ниже, подробности — `deploy/helm/mgate/README.md`.
3. **All-in-one образ** (`docker/aio/`) — все сервисы в одном контейнере для
   минимальных инсталляций. Запланирован, но **пока не опубликован** в реестре
   и не входит в релизы; см. [раздел 7](#7-all-in-one-образ-aio).

## 1. Требования к серверу

- Публичный статический IPv4 (и, желательно, IPv6) адрес.
- **Порт 25 открыт в обе стороны.** Многие облачные провайдеры (AWS,
  GCP, Azure, DigitalOcean, Hetzner Cloud и др.) блокируют исходящий 25 по
  умолчанию для новых аккаунтов — уточните и, если нужно, запросите
  разблокировку заранее (обычно через тикет в поддержку), иначе исходящая
  почта не будет доставляться.
- **Обратная DNS-запись (PTR)** для IP сервера, указывающая на
  `MGATE_HOSTNAME` (например `mail.example.com`). Без корректного PTR
  большинство почтовых систем (Gmail, Outlook и т.д.) будут отклонять или
  помечать письма как спам. PTR настраивается у провайдера сервера
  (хостинг/облако), не в вашей DNS-зоне.
- Рекомендуется 4 vCPU / 8 GB RAM (профиль `clamav` включён); минимум 2 GB
  RAM без `clamav` (см. `README.md` → Требования).
- Домен, которым вы управляете (доступ к DNS-зоне) — для MX/SPF/DKIM/DMARC
  и т.д. (см. `docs/DNS.md`).

## 2. Firewall / открываемые порты

| Порт | Протокол | Назначение | Обязателен |
|---|---|---|---|
| 25/tcp | SMTP | приём почты от других MTA | да |
| 465/tcp | SMTPS | отправка (submission, wrapper TLS) | да, если используете эту схему клиента |
| 587/tcp | Submission | отправка (STARTTLS) | да (рекомендуемый порт для клиентов) |
| 143, 993/tcp | IMAP / IMAPS | почтовые клиенты | да |
| 110, 995/tcp | POP3 / POP3S | почтовые клиенты (если используется POP3) | опционально |
| 4190/tcp | ManageSieve | управление серверными фильтрами из клиентов/веб-морды | да, если используются Sieve-фильтры через внешние клиенты |
| 80/tcp | HTTP | редирект на HTTPS (в будущем — ACME HTTP-01) | рекомендуется |
| 443/tcp | HTTPS | админка, личный кабинет, webmail, API | да |

Все остальные порты сервисов (`8080-8082`, `10040`, `7070`, `11332-11334`,
`5432`, `6379`, `3310`, `9900`, `12340`, `12345`, `24` и т.д. — см.
[`ARCHITECTURE.md`](ARCHITECTURE.md)) — **только на внутренней `backend`-сети Docker**,
наружу не публикуются и не должны проходить через внешний firewall хоста
вообще (compose их и не публикует). Firewall хоста должен разрешать входящие
только на порты из таблицы выше плюс SSH — всё остальное закрыто на уровне
docker-compose (нет `ports:`) и, опционально, дополнительно ужесточается
профилем `firewall` (nftables, см. `docker/firewall/`).

## 3. Установка (пошагово)

Для автоматической подготовки сервера используйте [установщик install.sh](https://raw.githubusercontent.com/mgate-server/mgate/main/scripts/install.sh):

```sh
curl -fsSL https://raw.githubusercontent.com/mgate-server/mgate/main/scripts/install.sh -o install-mgate.sh && sudo bash install-mgate.sh
```

Он спросит домен, FQDN сервера и e-mail администратора, установит недостающие зависимости
на Debian/Ubuntu, проверит ресурсы, порты и сети, скачает релиз, запустит контейнеры и
подключит почтовый домен. Параметры и поведение повторного запуска описаны в
[README](../README.md#автоматическая-установка-одной-командой). DNS и PTR изменяются у
провайдера вручную; доверенный TLS-сертификат загружается в панели администратора.

Ниже — ручная установка того же Docker Compose стека.

```sh
git clone https://github.com/mgate-server/mgate.git
cd mgate
git checkout v<версия>          # последний релиз: https://github.com/mgate-server/mgate/releases
make init                       # .env из .env.example + сгенерированные секреты
```

Отредактируйте `.env`:
- `MGATE_HOSTNAME` — FQDN сервера (MX target, HELO, хост админки/webmail).
- `MGATE_ADMIN_EMAIL` — email первого суперадминистратора.
- `MGATE_ADMIN_PASSWORD` — задайте, либо оставьте пустым: тогда при первом
  запуске контейнер `migrate` сгенерирует пароль и **выведет его в лог один
  раз** (прочитать: `docker compose logs migrate | grep -A2 'initial
  superadmin'`). Сохраните пароль сразу; повторно он не показывается.
- `MGATE_REGISTRY` — реестр образов; по умолчанию `ghcr.io/mgate-server`
  (публичный, анонимное скачивание). Меняйте только если используете
  собственное зеркало (см. [`CONFIGURATION.md`](CONFIGURATION.md)).
- `MGATE_VERSION` — версия релиза в формате CalVer (`2026.10.1`, без префикса
  `v`); должна совпадать с выбранным git-тегом. См. [раздел 5](#5-обновления-и-пиннинг-версий).
- `MGATE_ACME_*` — параметры встроенного автоматического выпуска сертификатов (Let's Encrypt / ZeroSSL,
  HTTP-01 и DNS-01), включены по умолчанию (`MGATE_ACME_ENABLED=true`), см. раздел [TLS](#4-tls-сертификаты).
- Секреты (`POSTGRES_PASSWORD`, `MGATE_SECRET_KEY`, `MGATE_INTERNAL_TOKEN` и
  т.д.) уже сгенерированы `make init` — не публикуйте `.env` нигде.
- `COMPOSE_PROFILES` — по умолчанию `clamav`; уберите `clamav`, если сервер
  не тянет антивирус (см. Требования в `README.md`), добавьте `backup`
  и/или `firewall`, если нужны соответствующие сервисы (профили независимы
  друг от друга).

Настройте DNS-записи вашего домена **до** первого запуска (см.
`docs/DNS.md`) — по крайней мере MX и A/AAAA на IP сервера; SPF/DKIM/DMARC
можно донастроить сразу после первого входа в мастере DNS в админке (ключ
DKIM генерируется при создании домена в `mgate`).

```sh
docker compose pull
docker compose up -d
docker compose logs -f migrate   # дождитесь завершения миграций
docker compose logs migrate | grep -A2 'initial superadmin'   # пароль администратора, если он не был задан в .env
```

Если пароль утерян, задайте новый:
`docker compose exec api mgate admin reset-password <MGATE_ADMIN_EMAIL>`.

Первый вход: `https://<MGATE_HOSTNAME>/admin`, логин — `MGATE_ADMIN_EMAIL`.
Смените пароль сразу после первого входа, если он был сгенерирован
автоматически. Двухфакторная аутентификация (TOTP) пока в разработке — вход выполняется
только по паролю, поэтому задайте длинный уникальный пароль суперадминистратора и
ограничьте доступ к `/admin` на уровне сети, если это возможно.

Проверка здоровья стека: `curl https://<MGATE_HOSTNAME>/api/v1/system/health`
→ `{"status":"ok"}`; `make smoke` прогоняет более полный дымовой сценарий
(`docs/TESTING.md`).

## 4. TLS-сертификаты

В MGate встроен автоматический ACME-клиент (Let's Encrypt / ZeroSSL, HTTP-01 и DNS-01),
который управляет сертификатами «из коробки»:

1. **Автоматический выпуск (по умолчанию):**
   При старте системы с `MGATE_ACME_ENABLED=true` фоновый воркер автоматически регистрирует/восстанавливает
   ACME-аккаунт и заказывает валидный TLS-сертификат для FQDN сервера (`MGATE_HOSTNAME`) и активных доменов.
   - До завершения выпуска почтовые контейнеры и Traefik временно используют самоподписанный bootstrap-сертификат из `/certs/default`.
   - Как только ACME-сертификат получен, он сохраняется в PostgreSQL (с шифрованием приватного ключа) и автоматически деплоится в `/certs/live/<name>/`, `/certs/default/` и динамический конфиг Traefik `10-certs.yml`. Сервисы подхватывают его на лету без перезапуска.
   - Продление выполняется воркером автоматически (проверка каждые 12 часов за 30 дней до истечения срока) или вручную кнопкой «Обновить» в веб-интерфейсе админки.
2. **Кастомные сертификаты (альтернатива):**
   При необходимости можно отключить ACME (`MGATE_ACME_ENABLED=false`) или загрузить собственный сертификат
   в админке: раздел «Сертификаты» → «Загрузить сертификат». Нужны цепочка сертификатов (сертификат сервера
   первым, затем промежуточные) и **незашифрованный** закрытый ключ в формате PEM; PKCS#12 не принимается.
   Сертификат, покрывающий `MGATE_HOSTNAME`, автоматически становится сертификатом по умолчанию для SMTP/IMAP и веб-интерфейса.
3. Сертификаты с источником `uploaded` можно обновлять загрузкой новой цепочки/ключа, а сертификаты с источником `acme` обновляются автоматически фоновым воркером или вручную в UI.

## 5. Обновления и пиннинг версий

Обновление стандартного Docker Compose одной командой, включая старые версии без обновлятора:

```sh
curl -fsSL https://raw.githubusercontent.com/mgate-server/mgate/main/scripts/update.sh | sudo bash -s -- --yes
```

Команда определяет каталог установки, создаёт копию базы и настроек и обновляет MGate.
На хостах с systemd автоматически подключаются обновления из панели. Последующие обновления:
та же команда, `sudo ./scripts/update.sh` или **Настройки сервера → Обновления**. Подключение службы,
первый переход и восстановление — в [UPDATES.md](UPDATES.md).

**Схема версий.** MGate использует CalVer `YYYY.M.N`: год, месяц **без
ведущего нуля** и порядковый номер сборки внутри месяца (с 1), например
`2026.10.1`. Git-теги — `v2026.10.1`; **теги образов — без `v`**: `2026.10.1`.
Версия едина для всего продукта: десять образов (`mgate`, `mgate-agent`,
`web`, `postfix`, `dovecot`, `rspamd`, `unbound`, `traefik`, `backup`,
`firewall`), Helm-чарт и backend. Для каждого релиза публикуются теги
`2026.10.1` (неизменяемый), `2026.10` (плавающий: последняя сборка месяца) и
`latest` (последний релиз). Текущая версия репозитория записана в файле
`VERSION` в корне.

`MGATE_VERSION` в `.env` управляет тегом всех образов
(`${MGATE_REGISTRY}/<service>:${MGATE_VERSION}`). **Не оставляйте
`MGATE_VERSION=latest` в продакшене** — зафиксируйте конкретную версию
(например, `MGATE_VERSION=2026.10.1`) после каждого осознанного обновления,
чтобы `docker compose pull` не подтягивал незапланированные изменения при
перезапуске хоста. Все образы одного релиза опубликованы с одной и той же
версией, поэтому менять нужно только эту переменную.

Обновление (Docker Compose):

1. Прочитайте [`CHANGELOG.md`](../CHANGELOG.md) и заметки релиза в
   [GitHub Releases](https://github.com/mgate-server/mgate/releases) (вендор
   публикует их вместе с каждой версией) — особенно внимательно, если между
   версиями прошло несколько месяцев. Сделайте резервную копию
   ([`docs/BACKUP.md`](BACKUP.md)).
2. Переключите клон на новый релиз, чтобы `docker-compose.yml`, `.env.example`
   и скрипты соответствовали версии образов:
   ```sh
   git fetch --tags && git checkout v<новая>   # например, v2026.11.1; на ветке main достаточно git pull
   ```
3. Выполните `make init` — команда добавит в `.env` новые переменные, а
   существующие значения оставит нетронутыми — в том числе ваши собственные
   переменные, которых нет в `.env.example` (прежний файл сохраняется как
   `.env.bak`).
4. Укажите в `.env` `MGATE_VERSION=<новая>` (без префикса `v`).
5. Выполните:
   ```sh
   docker compose pull
   docker compose up -d      # сервис `migrate` применяет миграции БД первым
   ```

**Откат.** Выполните `git checkout v<прежняя>`, верните прежнее значение
`MGATE_VERSION` и повторите `docker compose pull && docker compose up -d`.
Образы с точным тегом неизменяемы, поэтому прежняя версия гарантированно та
же. Учтите, что миграции БД односторонние: если новая версия уже изменила
схему, восстановите базу из резервной копии, сделанной перед обновлением
([`docs/BACKUP.md`](BACKUP.md)) — иначе старая версия может не запуститься.

**Свой реестр / зеркало.** Если сервер не имеет доступа к `ghcr.io`, скачайте
образы нужной версии, загрузите их в собственный реестр и укажите его в
`MGATE_REGISTRY` (все десять образов проекта должны лежать под одним префиксом
и с одинаковым тегом). `MGATE_REGISTRY` **не** распространяется на три
сторонних образа, которые `docker-compose.yml` скачивает из их собственных
реестров (Docker Hub): `postgres:18-alpine`, `valkey/valkey:9.0.6-alpine` и
`clamav/clamav:1.5.4-debian13-slim` (актуальные теги — в `docker-compose.yml`).
Для изолированной сети зеркалируйте и их и поменяйте значения `image:` в
compose-файле (или в override-файле); учтите и анонимные лимиты Docker Hub на
скачивание.

Не смешивайте образы разных версий внутри одной инсталляции: SPA и API
выпускаются и тестируются вместе. Автоматической проверки совместимости версий
SPA и API в рантайме (баннера «требуется обновление») пока нет — она
запланирована (см. [`UI-DEVELOPMENT.md`](UI-DEVELOPMENT.md) §7).

## 6. Helm chart (Kubernetes)

Production-grade Helm-чарт расположен в `deploy/helm/mgate/`:
* Полная поддержка секретов: генерация по умолчанию либо интеграция с `ExternalSecret`/`SealedSecret` через `.Values.secrets.existingSecret`.
* Хранилища: StatefulSet для `postgres`, `valkey`, `dovecot` (`vmail`) с поддержкой любых `StorageClass` (NFS, Ceph, EBS, local-path).
* Сетевые политики: встроенные жесткие `NetworkPolicy` для каждого пода.
* Отказоустойчивость: PodDisruptionBudget для stateless-компонентов (`api`, `webmail`, `web`, `rspamd`); число реплик задаётся в values.

Проверка и рендеринг:
```sh
docker run --rm -v "$PWD:/work" -w /work alpine/helm:4.3.0 lint deploy/helm/mgate
docker run --rm -v "$PWD:/work" -w /work alpine/helm:4.3.0 template mgate deploy/helm/mgate > /dev/null
helm install mgate deploy/helm/mgate -f my-values.yaml
```
Переменные окружения отдельных компонентов (например, `MGATE_WEBMAIL_TRUSTED_PROXIES`) задаются
через `api.extraEnv`, `webmail.extraEnv`, `worker.extraEnv`.

Подробное руководство по параметрам — в [`deploy/helm/mgate/README.md`](../deploy/helm/mgate/README.md).

## 7. All-in-one образ (AIO)

> **Статус:** образ запланирован и **пока не опубликован** в реестре, в релизы не входит. Ниже описан его дизайн; для продакшена используйте Docker Compose или Helm.

Для развёртывания на одном сервере без `docker compose` (PaaS/VPS провайдеры с одиночными контейнерами) разрабатывается AIO-образ (`docker/aio/`):
* Все сервисы запускаются под супервизором **s6-overlay v3** с контролем очередей инициализации `s6-rc`.
* Все персистентные данные объединены в едином каталоге `/var/lib/mgate-aio` (`postgres`, `valkey`, `vmail`, `certs`, `dkim`).
* Подробная раскладка данных, процедуры горячего бэкапа и сайзинг описаны в [`docker/aio/README.md`](../docker/aio/README.md).

## 8. Внешние базы данных, сетевые ФС и высокая доступность

Для масштабирования за пределы одного сервера:
- **Внешний PostgreSQL**: задайте `MGATE_DATABASE_URL` (или `.Values.externalDatabase` в Helm) на внешний отказоустойчивый кластер (Patroni, CloudNativePG, AWS RDS Multi-AZ).
- **Внешний Valkey / Redis**: задайте `MGATE_REDIS_URL` (или `.Values.externalValkey` в Helm). Нужна **одна точка подключения** (один хост — обычный экземпляр или управляемый сервис с единым endpoint, например primary-endpoint с репликацией). Redis Cluster и Sentinel не поддерживаются: бэкенд не умеет ни кластерной маршрутизации по слотам, ни обнаружения мастера через Sentinel.
- **Сетевые файловые системы для `/var/vmail`**:
  - **NFS v4**: обязательные флаги монтирования `rw,noatime,nodiratime,hard,intr,actimeo=1` для предотвращения рассинхронизации индексов Dovecot.
  - **JuiceFS**: распределённая POSIX ФС поверх S3/MinIO с кэшированием на локальных NVMe-дисках нод.
- **Отказоустойчивость (HA)**: полный регламент, сценарии отказов (потеря узла Postfix или Dovecot, split-brain) и методы их митигации собраны в документе [`docs/HA.md`](HA.md).

## 9. Прокси, CDN и балансировщики: реальный IP пользователей

Веб-вход и смена пароля ограничивают подбор паролей по IP пользователя (задержка, затем
`429` с `Retry-After`), поэтому бэкенд должен видеть адрес самого пользователя, а не
промежуточного узла.

Адрес берётся так: если TCP-пир входит в `MGATE_WEBMAIL_TRUSTED_PROXIES`, заголовок
`X-Forwarded-For` читается справа налево, адреса из этого списка пропускаются, и первый адрес вне
списка считается адресом пользователя. Левее него заголовок не читается (его мог прислать сам
клиент). Значит, **каждый** прокси между пользователем и MGate должен быть в списке:

- **Docker Compose без внешних прокси.** Traefik принимает соединения напрямую и сам добавляет
  `X-Forwarded-For`; значение по умолчанию подходит. Чтобы сузить список до самого Traefik,
  укажите подсеть сети `public` (её выбирает Docker:
  `docker network inspect <проект>_public --format '{{(index .IPAM.Config 0).Subnet}}'`) или
  закрепите эту подсеть в своём override-файле compose. В rootless Docker встроенный драйвер
  проброса портов (`builtin`) не передаёт адрес источника — используйте драйвер `slirp4netns`
  или обычный (rootful) Docker.
- **CDN или L7-балансировщик (HTTP) перед Traefik.** Traefik должен принимать от них
  `X-Forwarded-For` (`entryPoints.<имя>.forwardedHeaders.trustedIPs` с их подсетями — иначе он
  отбросит заголовок и подставит адрес балансировщика), а в `MGATE_WEBMAIL_TRUSTED_PROXIES`
  должны быть и подсети CDN/балансировщика, и адрес Traefik.
- **L4-балансировщик (TCP), подменяющий адрес источника** (SNAT; в Kubernetes — Service
  `type: LoadBalancer` с `externalTrafficPolicy: Cluster`): адрес пользователя не доходит ни до
  Traefik, ни до ingress-контроллера. Включите PROXY protocol между балансировщиком и
  Traefik/ingress (`entryPoints.<имя>.proxyProtocol.trustedIPs` в Traefik, аналогичная настройка
  у вашего ingress-контроллера) либо `externalTrafficPolicy: Local`.
- **Kubernetes (Helm).** Значение по умолчанию охватывает частные диапазоны, в которых обычно
  лежит CIDR подов, а с ним и ingress-контроллер. Если CIDR подов вне их (например,
  `100.64.0.0/10`), заголовок от ingress не принимается, и все пользователи видны под адресом его
  пода. Переопределите список через `api.extraEnv` и `webmail.extraEnv` (одно и то же
  значение обоим; веб-вход обслуживает `api`, веб-почту — `webmail`):

  ```yaml
  api:
    extraEnv:
      - { name: MGATE_WEBMAIL_TRUSTED_PROXIES, value: "100.64.0.0/10, 127.0.0.0/8" }
  webmail:
    extraEnv:
      - { name: MGATE_WEBMAIL_TRUSTED_PROXIES, value: "100.64.0.0/10, 127.0.0.0/8" }
  ```

  Необязательный дополнительный лимит частоты для `/api/v1/auth` на ingress (nginx-ingress,
  Traefik) описан в `deploy/helm/mgate/README.md`.

**Общий адрес.** Если обход заголовка закончился на адресе из списка — например, все
пользователи видны под адресом узла или балансировщика, который сам входит в список по
умолчанию, — бэкенд считает этот адрес собственным адресом прокси, общим для многих
пользователей. Для него действуют отдельные пределы:

- задержка растёт с числом неудач (от 3 до 15 с) — для всех за этим адресом;
- после 100 неверных паролей за 10 минут веб-вход с этого адреса закрывается (`429`) для всех
  за ним до конца окна (для адреса одного пользователя порог — 10);
- одновременно проверяется не больше 16 паролей с этого адреса, лишние запросы сразу получают
  `429`;
- «знакомым» для логина (ниже) такой адрес не бывает: атакующий и владелец за ним неразличимы.

Подбор паролей так остаётся ограниченным, но цена высока: любой за этим адресом сотней неверных
паролей может на 10 минут закрыть веб-вход всем остальным. Поэтому по возможности передавайте
реальный адрес пользователя (PROXY protocol, `externalTrafficPolicy: Local`). Адрес, которого нет
в списке, но за которым много людей (например, внешний адрес офисного NAT), считается адресом
одного пользователя: десяток неверных паролей закроет вход всем за ним на 10 минут.

**Предел на логин.** Если к одному логину за 10 минут пришло 50 неверных паролей с адресов, с
которых в него ещё не входили, вход в этот логин с любого такого адреса до конца окна
отклоняется (`429`, даже с верным паролем), а одновременно проверяется не больше 4 паролей к
нему с незнакомых адресов. С адресов, откуда владелец уже успешно входил (они запоминаются на
30 дней), вход работает как обычно. Тот же предел действует для IMAP, POP3 и SMTP AUTH: почтовый
клиент на привычном адресе продолжает работать, а на новом (например, телефон в чужой сети) во
время такой атаки получает отказ. Общий адрес знакомым не бывает: если все пользователи видны
под ним, атака на логин закрывает его веб-вход для всех.

Обратное тоже верно: в списке не должно быть сетей, из которых обычные пользователи подключаются
к Traefik напрямую (офис, VPN в частных диапазонах), — их адреса тоже считались бы общими
адресами прокси (высокий порог, нет «знакомых» адресов). Значение по умолчанию охватывает все
частные сети; в таком случае сузьте его до подсетей прокси. Порты API и шлюза веб-почты не
должны быть доступны пользователям в обход прокси.
