# 0009. Разделение на публичный комплект развёртывания и закрытый backend

Статус: Принято

Дата: 2026-09-12; модель публикации и версионирования — 2026-10-07

Связано: ADR [0003](0003-single-binary-components-extensions.md),
[0007](0007-editions-and-licensing-model.md), [0014](0014-license-choice.md);
[DEPLOYMENT.md](../DEPLOYMENT.md) §5, [ARCHITECTURE.md](../ARCHITECTURE.md) §7

## Контекст

Продукт состоит из частей разной природы:

- **комплект развёртывания** (compose-файлы, Helm-чарт, скрипты установки), **конфигурация и
  Dockerfile образов** почтового стека и инфраструктуры (Postfix, Dovecot, Rspamd, Unbound,
  Traefik, резервное копирование, firewall) и **SPA** (админ-панель, личный кабинет,
  веб-почта). Это то, что оператор разворачивает, настраивает и отлаживает сам; ему важно
  видеть, что именно работает на его сервере, какие порты открыты и как настроены почтовые
  демоны;
- **backend** (API, шлюз веб-почты, фоновые задачи, лицензирование), исходный код которого не
  публикуется (ADR [0007](0007-editions-and-licensing-model.md));
- **сервер лицензий и кабинет клиента** — сервис вендора, который вообще не входит в
  поставку.

Нужно было решить, где живёт публичный код, как он связан с закрытым backend, как продукт
выпускается и версионируется и как внешние участники могут сообщать о проблемах и предлагать
изменения.

## Решение

1. **Этот репозиторий** — публичный, https://github.com/mgate-server/mgate. Он содержит
   комплект развёртывания (`docker-compose*.yml`, `deploy/helm/mgate`, `deploy/systemd`,
   `scripts/`), Dockerfile и конфигурацию образов (`docker/`), исходный код SPA (`web/`),
   тесты (`tests/`) и документацию (`docs/`). Кода backend, `Cargo.*` и миграций БД здесь
   нет и не будет.
2. **Backend закрыт** и распространяется только образами `ghcr.io/mgate-server/mgate` и
   `ghcr.io/mgate-server/mgate-agent` (ADR [0003](0003-single-binary-components-extensions.md)).
   Публичный репозиторий взаимодействует с ним только через задокументированный интерфейс
   ([ARCHITECTURE.md](../ARCHITECTURE.md) §7). Сервер лицензий не распространяется ни в каком
   виде.
3. **Образы.** Все 10 образов продукта публикуются в GitHub Container Registry в пространстве
   имён `ghcr.io/mgate-server` и доступны для анонимного `pull`: `mgate`, `mgate-agent`
   (закрытый backend), `web`, `postfix`, `dovecot`, `rspamd`, `unbound`, `traefik`, `backup`,
   `firewall`. Пока публикуется только платформа `linux/amd64`. Список пакетов —
   https://github.com/orgs/mgate-server/packages. Каждый образ несёт OCI-метки
   `org.opencontainers.image.source`/`.url` = `https://github.com/mgate-server/mgate`
   (по ним GHCR связывает пакет с репозиторием) и `org.opencontainers.image.version` = версия
   релиза.
4. **Версионирование — CalVer `YYYY.M.N`**: год, месяц **без ведущего нуля**, номер сборки
   внутри месяца начиная с 1 (например, `2026.10.1`). Строка остаётся валидной SemVer, поэтому
   её принимают Helm и npm. Версия **одна на весь продукт**: все 10 образов, Helm-чарт
   (`version` и `appVersion`) и backend. Git-теги — `v2026.10.1`; текущая версия записана в
   файле `VERSION` в корне репозитория. Теги образов для каждого релиза: `2026.10.1`
   (неизменяемый), `2026.10` (плавающий: последняя сборка месяца), `latest` (последний релиз).
   Первый публичный релиз — `2026.10.1`.
5. **Публикация.** Релиз выполняет вендор из собственного контролируемого окружения сборки:
   собираются все 10 образов, проходят smoke-проверку, публикуются в GHCR; затем в GitHub
   публикуется **чистый снимок** дерева этого репозитория — один коммит на релиз, без истории
   промежуточной разработки — и создаётся GitHub Release с тегом `vYYYY.M.N`. Номера версий
   в `VERSION`, `deploy/helm/mgate/Chart.yaml`, `package.json` и значение `MGATE_VERSION` в
   `.env.example` выставляет релизный процесс, а не правка вручную. CI в GitHub
   (`.github/workflows/ci.yml`) выполняет только линтинг, тесты и проверочную сборку — он не
   публикует образы и не создаёт релизы.
6. **Разработка и внешние вклады.** Разработка ведётся во внутреннем репозитории вендора;
   репозиторий на GitHub получает релизные снимки. Issues и pull request'ы на GitHub
   рассматривают мейнтейнеры; принятые изменения переносятся во внутреннее дерево и появляются
   в следующем релизном снимке (pull request при этом не сливается на GitHub напрямую).
   Порядок участия — `CONTRIBUTING.md`, правовые условия — ADR [0014](0014-license-choice.md).
   Об уязвимостях сообщают приватно:
   https://github.com/mgate-server/mgate/security/advisories/new (см. `SECURITY.md`).

## Альтернативы

- **Один публичный монорепозиторий с кодом backend.** Невозможен: исходный код backend не
  публикуется (ADR [0007](0007-editions-and-licensing-model.md)).
- **Git submodule на закрытый код внутри публичного репозитория.** Ломает клонирование для
  всех, у кого нет доступа к закрытому коду, и ничего не даёт тем, у кого он есть. Отклонено:
  публичная часть зависит только от опубликованных образов.
- **Зеркалирование полной истории разработки на GitHub.** Отклонено: история содержит
  промежуточные состояния и внутренние рабочие материалы, а снимок на релиз даёт однозначное
  соответствие «git-тег ↔ версия образов». Цена — история изменений на GitHub состоит из
  релизных коммитов; изменения между релизами описываются в `CHANGELOG.md` и заметках
  GitHub Release.
- **Сборка и публикация образов CI-конвейером на GitHub.** Отклонено: закрытые образы backend
  нельзя собрать из публичного репозитория, а согласованный выпуск всех 10 образов под одной
  версией проще и надёжнее обеспечить одним процессом у вендора; учётные данные публикации при
  этом не хранятся в CI публичного репозитория.
- **SemVer `MAJOR.MINOR.PATCH`.** Отклонено в пользу CalVer: продукт выпускается как единое
  целое с регулярным ритмом, и по версии сразу виден возраст релиза; при этом CalVer-строка
  совместима с инструментами, ожидающими SemVer.
- **Мультиархитектурные образы с первого релиза.** Отложено: пока только `linux/amd64`.

## Последствия

- Оператор получает всё из двух публичных мест без авторизации: код, релизы и issues —
  https://github.com/mgate-server/mgate, образы — `ghcr.io/mgate-server`.
- Обновление продукта — смена одного значения `MGATE_VERSION` для всех образов; для
  production рекомендуется закреплять полный тег (`2026.10.1`), а не `latest`
  ([DEPLOYMENT.md](../DEPLOYMENT.md) §5). Образы разных версий внутри одной установки не
  смешиваются.
- Пересобрать backend из исходников нельзя; для локальной разработки публичной части
  используется опубликованный образ backend, который при необходимости переопределяется
  переменными `MGATE_IMAGE`/`MGATE_AGENT_IMAGE`. Образы, которые принадлежат этому
  репозиторию, собираются локально через `docker-compose.build.yml`.
- Pull request'ы не сливаются на GitHub напрямую — автор видит результат в следующем
  релизе; это должно быть ясно описано в `CONTRIBUTING.md`.
- Права на код этого репозитория и на образы определяются `LICENSE` и `EULA.md` (ADR
  [0014](0014-license-choice.md)).
