# 0010. Конвейер логов и событий

Статус: Принято

Дата: 2026-09-12

## Контекст

Продукту нужны «Live Logs» — просмотр SMTP-сессий, IMAP-авторизаций и
Rspamd-оценок в реальном времени с фильтрацией, в админ-панели. Источники событий —
процессы Postfix и Dovecot (пишущие в syslog) и Rspamd (у которого есть собственный
`metadata_exporter`, умеющий слать структурированные события по HTTP). Нужен путь от
«строка в syslog внутри контейнера postfix» до «строка в интерфейсе админа в реальном
времени», не теряющий события при кратковременной недоступности API/БД (см. режимы
отказа в `docs/ARCHITECTURE.md` §12 — приём почты не должен зависеть от API, но его
события всё равно должны попасть в лог, когда API снова доступен).

## Решение

Двухступенчатый конвейер:

1. **Захват**: `mgate-agent --role postfix|dovecot` внутри соответствующего контейнера
   слушает unix datagram socket `/dev/log` (то есть является syslog-приёмником для
   процессов в своём контейнере), эхом печатает каждую строку в stdout (чтобы `docker
   logs`/`json-file` драйвер продолжал работать как обычный способ отладки) и
   одновременно кладёт её в Valkey: `XADD mgate:logs MAXLEN ~ 200000 *` с полями `src ts
   host prog pid sev msg`. Rspamd отдельно (не через syslog) шлёт структурированные
   события через `metadata_exporter` → `POST http://api:8081/internal/v1/events/rspamd`
   — у него уже есть родные структурированные метаданные (спам-скор, симптомы,
   DKIM/DMARC-результат), которые не нужно повторно парсить из текстовой syslog-строки.
2. **Обработка**: `worker` читает стрим `mgate:logs` через consumer group `ingest`
   (`XREADGROUP`), парсит/нормализует записи и пишет в партиционированные по месяцу
   таблицы PostgreSQL (`mail_events`, `login_events`) — это единое хранилище для
   истории (в отличие от эфемерного стрима с `MAXLEN ~ 200000`, который служит только
   буфером на случай кратковременной недоступности `worker`). Просмотр в реальном
   времени в SPA — через Server-Sent Events (`GET /api/v1/admin/logs/stream`,
   обслуживается бэкендом), а не через прямое
   чтение стрима Valkey из браузера.

## Альтернативы

- **Прямая запись логов в PostgreSQL из postfix/dovecot** (например, через `syslog-ng`
  с SQL-дестинацией): добавляет ещё одну технологию (syslog-ng/rsyslog с SQL-модулем) и
  создаёт синхронную зависимость момента приёма письма от доступности PostgreSQL —
  противоречит принципу «доставка не должна падать вместе с БД» так же остро, как и для
  passdb (ADR-0004); Valkey как буфер даёт естественную развязку по времени.
  Дополнительно: Postfix/Dovecot и так пишут в syslog нативно — не нужно их
  переконфигурировать под нестандартный дестинейшн.
- **Отправка логов напрямую в стороннюю систему (Loki/Elasticsearch) без собственной
  БД**: решает задачу просмотра логов, но не даёт единого источника для агрегированной
  статистики (`stats_hourly`) и не вписывается в требование «всё out-of-the-box без
  внешних зависимостей» (доп. компонент вне базового состава сервисов) — отклонено для
  MVP; ничто не мешает пользователю параллельно настроить экспорт `json-file`-логов в
  свой стек мониторинга самостоятельно (`docker logs`/log-driver остаются доступны,
  раз `mgate-agent` эхом печатает всё в stdout).
- **Rspamd тоже через syslog вместо `metadata_exporter`**: технически возможно, но
  `metadata_exporter` — штатный, документированный механизм Rspamd для структурированных
  вебхуков и не требует парсинга произвольного текстового формата логов Rspamd (который
  может меняться между версиями); выбран как более устойчивый интеграционный путь.
- **WebSocket вместо SSE для Live Logs**: SSE достаточен (однонаправленный поток от
  сервера, автоматический реконнект браузером), не требует управления двусторонним
  протоколом ради одностороннего потока событий; WS уже используется для веб-почты
  (IDLE-события), где обратный канал (клиент → сервер) действительно нужен.

## Последствия

- `mgate-agent` не пишет напрямую в PostgreSQL и не требует токена `MGATE_INTERNAL_TOKEN`
  для этого пути (только для своего control API `:7070`) — он общается только с Valkey
  внутри `backend`-сети.
- `mgate:logs` — единственный стрим; при длительной недоступности `worker`
  (> времени, за которое накопится 200000 записей при `MAXLEN ~`) старые записи
  вытесняются — зафиксированный, принятый риск потери части истории в этом крайнем
  случае (не потери самой почты — она продолжает доставляться независимо от логов).
- Партиционирование `mail_events`/`login_events` по месяцу — обязательное требование к
  миграциям схемы, чтобы ретеншн (`TODO(S2)`: политика очистки старых
  партиций) не требовал `DELETE` по всей таблице.
- Формат полей стрима (`src ts host prog pid sev msg`) фиксирован (см. `docs/ARCHITECTURE.md`
  §6.5) — парсер в `worker` должен быть терпим к отсутствующим полям (не все `prog`
  одинаково размечают состояние), это явный `TODO(S2)` для реализации.
