# 0018. SPA публична целиком (включая Pro-страницы); всё исполнение — на сервере

Статус: Принято

Дата: 2026-09-12

Связано: ADR [0003](0003-single-binary-components-extensions.md),
[0007](0007-editions-and-licensing-model.md), [0012](0012-single-spa-three-areas.md);
`docs/LICENSING.md`, `docs/UI-DEVELOPMENT.md`

## Контекст

SPA — открытая часть продукта: всё, что оператору нужно для запуска и адаптации
платформы, публично, включая исходники SPA (см. `docs/LICENSING.md`). Это ставит
явный архитектурный вопрос: раз SPA целиком открыта, а Pro-страницы физически показывают Pro-функциональность — не
ослабляет ли это защиту редакций? Нужно решение, которое отвечает на этот вопрос
прямо, а не оставляет его подразумеваемым.

## Решение

**SPA публична целиком, без исключений — включая код Pro-страниц.** Любой человек
может прочитать, собрать и изменить `web/apps/spa/src/pro/**`, включая версию,
которая всегда показывает Pro-контент независимо от реального энтайтлмента. Это
осознанно допустимо и не является уязвимостью, потому что:

1. Каждый Pro-эндпойнт API (`/api/v1/pro/*`) проверяет валидный энтайтлмент **на
   сервере**, независимо от того, что показывает или скрывает клиент
   (см. `docs/LICENSING.md` §13).
2. UI-гейт (`<ProFeature flag>`, пакет `packages/extensions`) существует только для
   UX — чтобы не показывать пользователю функцию, которой он не может воспользоваться
   — а не как барьер безопасности.
3. Ни один секрет (ключи, логика проверки лицензии) не попадает в SPA — тот код целиком
   в закрытом бэкенде.

Правило для всей кодовой базы и документации: **клиентский гейт никогда не
рассматривается как контроль безопасности**. Формулировка «UI-гейт косметический»
должна сопровождать каждое упоминание `<ProFeature>`/`ExtensionRegistry` в
документации, аналогично тому, как `docs/LICENSING.md` §13 требует не писать «взлом
невозможен» про бэкенд.

## Альтернативы

- **Публичная SPA, но Pro-UI отдельным закрытым пакетом с переключением при сборке.**
  Усложняет сборку без выигрыша в безопасности — JavaScript, отданный браузеру, всегда
  читаем и деминифицируем. Отклонено.
- **Скрывать даже наличие Pro-страниц для неэнтайтленных инсталляций (server-driven
  UI, бэкенд не отдаёт даже разметку меню).** Усложняет SPA (нужен отдельный API,
  диктующий структуру навигации) ради скрытия информации, которая не является
  секретом (список фич Pro и так публикуется в маркетинговых материалах и
  в `docs/LICENSING.md`).
  Отклонена как решение несуществующей проблемы.
- **Требовать серверный рендеринг (SSR) Pro-страниц, чтобы код не покидал сервер.**
  Меняет всю архитектуру фронтенда (SPA → SSR) ради того же нулевого выигрыша в
  безопасности, что и первая альтернатива — отклонена.

## Последствия

- Документация (`docs/ARCHITECTURE.md` §9, `docs/UI-DEVELOPMENT.md` §5,
  `docs/LICENSING.md`) обязана явно называть UI-гейт косметическим при каждом
  упоминании — предотвращает будущее ложное ощущение защищённости у тех, кто читает
  один из этих документов в отрыве от остальных.
- Pro-страницы (`web/apps/spa/src/pro/**`) — обычный код этой SPA, ревьюится и
  тестируется как любой другой код репозитория; не требует отдельного процесса
  релиза/сборки.
- Пункт навигации на Pro-раздел сейчас статичен (виден всем администраторам, гейтится
  только содержимое конкретных фич) — если продукт захочет иначе, это отдельное
  решение об UX, не о безопасности (см. открытый вопрос в ADR-0012 «Последствия»).
- Ничего не меняется в модели угроз для бэкенда (`docs/SECURITY.md`) — этот ADR
  описывает только SPA; вся защита редакций остаётся полностью на стороне закрытого
  бэкенда, как и раньше.
