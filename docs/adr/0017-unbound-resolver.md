# 0017. Резолвер Unbound (DNSBL, DNSSEC, DANE)

Статус: Принято

Дата: 2026-09-12

## Контекст

Почтовый стек и сервисы бэкенда MGate делают много внешних DNS-запросов, для которых
корректность и защищённость резолвинга напрямую влияет на безопасность и
доставляемость почты:

- **DNSBL/RBL-запросы** (Rspamd, Postfix postscreen) — миллионы lookups в чужие зоны;
  использование публичного резолвера провайдера (или резолвера хоста) для этого нежелательно
  по двум причинам: (а) многие публичные DNSBL-провайдеры ограничивают или блокируют
  запросы с публичных резолверов (требуют, чтобы запросы шли с "чистого" рекурсивного
  резолвера конкретной инсталляции — иначе легко словить троттлинг/бан IP резолвера,
  который делят тысячи чужих пользователей); (б) нужен предсказуемый, контролируемый
  самой инсталляцией резолвер для диагностики (какие ответы реально получены).
- **DNSSEC-валидация** — SPF/DMARC/MTA-STS/DKIM lookups и верификация чужих доменов
  выигрывают от защиты от DNS spoofing; обычный резолвер хоста (или Docker embedded DNS,
  который лишь форвардит) не обязательно валидирует DNSSEC.
- **DANE/TLSA** — для будущей поддержки DANE у исходящей почты (проверка TLS-сертификата
  получателя через TLSA-записи) требуется резолвер, которому можно доверять
  (DNSSEC-валидированный ответ) — без DNSSEC DANE бессмысленен (TLSA без валидации DNSSEC
  сам является вектором атаки).

## Решение

Отдельный сервис **`unbound`** (`${MGATE_REGISTRY}/unbound:${MGATE_VERSION}`,
Dockerfile в `docker/unbound/`) — DNSSEC-валидирующий рекурсивный резолвер, подключённый
к обеим сетям (`public` — для собственно рекурсивного резолвинга наружу; `backend` — со
статическим IP `${MGATE_RESOLVER_IP:-172.30.1.53}`, чтобы остальные сервисы могли
надёжно на него ссылаться конфигурацией `dns:`). Все контейнеры, которым нужно резолвить
внешние имена (Postfix, Rspamd, `api`/`worker`), настроены
`dns: [${MGATE_RESOLVER_IP:-172.30.1.53}]` — при этом Docker embedded DNS продолжает
резолвить имена сервисов друг друга (service discovery), не конфликтуя с unbound
(Docker embedded DNS по-прежнему
резолвит имена сервисов и перенаправляет остальные запросы на unbound).

Образ `unbound` **никогда не форвардит** запросы на чужие резолверы: только полная
рекурсия от корневых серверов (`root-hints`), без `forward-zone`, без LAN-адресов и без
`domain-insecure` для локальных зон. Если оператору нужно резолвить приватную зону
(например, внутреннюю `.local`/корпоративную), он добавляет собственные клаузы
(`forward-zone`, `stub-zone`, `local-zone`, `domain-insecure`) отдельными `*.conf`-файлами,
смонтированными в `/etc/unbound/conf.d/` (последняя строка шаблона — `include-toplevel` на
этот каталог; пустой каталог допустим). Подробности и пример — `docker/unbound/README.md`.

## Альтернативы

- **Резолвер хоста / Docker embedded DNS напрямую наружу**: не гарантирует DNSSEC-
  валидацию и не даёт предсказуемого, контролируемого самой инсталляцией исходящего IP
  для DNSBL-запросов — отклонено по причинам, изложенным в разделе «Контекст» выше.
- **Использовать публичный DNSSEC-резолвер (например, 1.1.1.1, 9.9.9.9) напрямую**:
  решает DNSSEC, но не решает проблему троттлинга DNSBL-провайдерами с общих публичных
  резолверов и добавляет внешнюю зависимость времени отклика (latency, доступность) в
  горячий путь приёма почты (postscreen/rspamd делают DNSBL-запросы синхронно на каждое
  соединение) — собственный кэширующий резолвер в той же docker-сети существенно
  быстрее и не зависит от доступности стороннего сервиса.
- **BIND9 вместо Unbound**: BIND умеет то же самое (рекурсия + DNSSEC), но существенно
  тяжелее по конфигурации и по потреблению ресурсов для роли "просто кэширующий
  DNSSEC-резолвер"; Unbound спроектирован специально для этой роли (validating,
  caching, recursive resolver) и легче в контейнеризации.
- **dnsmasq**: не валидирует DNSSEC (это форвардящий/кэширующий резолвер без полноценной
  рекурсии и валидации) — не подходит для требования DNSSEC/DANE.

## Последствия

- `docker/unbound/unbound.conf.template` должен явно перечислять upstream root hints/trust anchor и не быть
  открытым резолвером для интернета (только `public`/`backend` сети инсталляции, не публикуемый
  порт наружу — порт `unbound` на хост не публикуется, см. `docs/ARCHITECTURE.md` §4).
- Диагностика DNS-проблем (например, «письмо отклонено из-за DNSBL» в Live Logs) может
  ссылаться на конкретные ответы `unbound`, что упрощает саппорт по сравнению со
  сценарием, где резолвинг идёт через непрозрачный внешний сервис.
- Для DANE (TLSA-проверка исходящей почты) — сама поддержка на стороне Postfix
  (`smtp_tls_security_level = dane`) остаётся `TODO(S1)`, этот ADR фиксирует только то,
  что инфраструктурная предпосылка (доверенный DNSSEC-резолвер) уже удовлетворена.
- Если `unbound` недоступен — деградация зафиксирована в `docs/ARCHITECTURE.md` §12
  (Docker embedded DNS продолжает резолвить имена сервисов; внешний DNSSEC-резолвинг
  недоступен) — не дублируется здесь повторно.
