# 0012. Единая SPA с тремя областями, обслуживается собственным образом `web`

Статус: Принято

Дата: 2026-09-12

## Контекст

Продукт содержит три различных по аудитории интерфейса: админ-панель (SuperAdmin/
DomainAdmin), личный кабинет пользователя (self-service) и веб-почта (webmail),
плюс общая точка входа (`/login`). Нужно решить — это одно React-приложение с
маршрутизацией по разделам, или три (или больше) отдельных билда/деплоя. Дополнительно,
бэкенд предоставляет Pro-функции через собственные API-маршруты — на фронтенде
нужна точка расширения для Pro-страниц, которые показываются по ответу
`GET /api/v1/system/entitlements`.

## Раздача SPA

SPA целиком публична, включая Pro-страницы (`web/apps/spa/src/pro/**`): они гейтятся в
рантайме по ответу `GET /api/v1/system/entitlements`, а не флагом сборки. Секретов в UI
нет, вся защита — на сервере (см. ADR 0018).

Собранный бандл SPA раздаётся **отдельным образом `web`** (nginx, `docker/web/`).
Traefik маршрутизирует `/api/*`+`/.well-known/*` → `api`, `/api/v1/mail*` → `webmail`,
всё остальное → `web` (см. `docs/ARCHITECTURE.md` §2–§3).

## Решение

**Одна SPA** (`web/apps/spa`), три логические области-маршрута: `/admin/*`
(включая `/admin/pro/*`), `/account/*`, `/mail/*`, плюс `/login`. Общие вещи
(аутентификация, i18n, тема, общий API-клиент, компоненты дизайн-системы
`packages/ui`) переиспользуются напрямую, без дублирования сборки.

**Гейтинг Pro-UI — рантайм, не сборка.** Пакет `packages/extensions`
предоставляет `<ProFeature flag>` и `ExtensionRegistry` — Pro-страницы
(`web/apps/spa/src/pro/**`) регистрируют свои пункты навигации/панели/виджеты один
раз при старте (статически, как обычный код SPA), а видимость их *содержимого*
управляется живым списком энтайтлментов (`setEntitlementFlags()`,
`useSyncExternalStore`).

## Альтернативы

- **Три отдельных SPA (admin.js, account.js, mail.js)**: изоляция бандлов, но
  дублирование общей инфраструктуры (аутентификация, роутинг верхнего уровня, общий
  API-клиент, тема) в трёх местах и худший UX при переходе между разделами. Отклонено.
- **Micro-frontends (Module Federation)**: избыточная сложность для проекта такого
  размера на этом этапе; выигрыш (независимые деплои разделов) не нужен.
- **Отдельная сборка SPA для Pro (переключение модулей при сборке).** Две сборки
  расходятся по исправлениям, а скрывать Pro-UI бессмысленно — JavaScript, отданный
  браузеру, всегда читаем. Отклонено (ADR 0018).

## Последствия

- `packages/extensions` — публичный пакет: `ExtensionRegistry` (статические UI-вклады),
  `<ProFeature>` (реактивный гейт по живым энтайтлментам), типы `NavItem`/
  `SettingsPanel`/`DashboardWidget`/`FeatureFlags`. Модель «один бандл, одна сборка»
  соответствует ADR-0003: редакция — свойство рантайма, а не сборки.
- Собранный `web/apps/spa/dist` копируется в отдельный образ `web`
  (`docker/web/Dockerfile`, nginx, non-root, read-only rootfs), не в образ бэкенда.
  Runtime-конфигурация (`MGATE_API_BASE_URL` и необязательные ссылки на тарифы и портал вендора) рендерится в `/config.json`
  entrypoint'ом этого образа при старте контейнера (`docs/UI-DEVELOPMENT.md` §4) — один
  и тот же образ работает под любым доменом без пересборки.
- Все три области используют один и тот же сгенерированный из опубликованного
  бэкендом OpenAPI-документа API-клиент (`packages/api-client`, `make openapi-sync`),
  что означает: расширение публичного API немедленно доступно всем разделам SPA без
  отдельной интеграции на клиенте.
- Единая точка логина (`/login`) должна уметь редиректить в нужную область по роли
  пользователя после аутентификации (SuperAdmin/DomainAdmin → `/admin`, User → `/account`
  или `/mail` в зависимости от того, что он открывал).
- Видимость пункта навигации на Pro-раздел (не только его содержимого) пока не
  фильтруется по живым энтайтлментам (статический список) — если продукт захочет
  скрывать сам пункт меню для неэнтайтленных инсталляций, `ExtensionRegistry.getNavItems()`
  тоже должен подписаться на живой список.
