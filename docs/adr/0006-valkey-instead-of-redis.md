# 0006. Valkey вместо Redis

Статус: Принято

Дата: 2026-09-12

## Контекст

Исходно в качестве технологии для очередей/кэша/сессий/rate limiting рассматривался Redis.
С марта 2024 Redis (Redis Ltd.) изменил лицензию основного дистрибутива (с BSD на
двухвариантную RSALv2/SSPLv1, несовместимую с большинством дистрибутивов Linux и с
классическим определением open source), что напрямую касается проекта, который сам
пытается решить непростую задачу лицензирования собственного кода и
не должен усложнять себе (и пользователям, разворачивающим MGate) соответствие лицензиям
зависимостей. Valkey — форк Redis 7.2 под Linux Foundation, сохраняющий открытую
лицензию (BSD-3-Clause) и протокольную/API-совместимость с Redis (клиентские
библиотеки, включая крейт `redis` для Rust, работают с Valkey без изменений).

## Решение

Использовать **Valkey** (`valkey/valkey:9.0-alpine`) вместо Redis везде, где требуется
in-memory-хранилище: сессии, rate limiting, IP-баны, стрим логов
(`mgate:logs`), а также как хранилище
Rspamd (Bayes, ratelimit, DKIM/ARC-ключи, отдельная логическая БД — `db 1`). Название
переменной окружения оставлено `MGATE_REDIS_URL` (а не `MGATE_VALKEY_URL`) намеренно —
это protocol-level имя (RESP-протокол остаётся "redis://"-схемой у клиентских библиотек,
включая крейт Rust `redis` и конфигурацию Rspamd `servers = "valkey:6379"` с
`type = redis`), смена имени переменной не даёт архитектурной выгоды и усложнила бы
совместимость с документацией и клиентскими библиотеками, которые сами используют это
имя схемы.

## Альтернативы

- **Оставить Redis, зафиксировав старую (BSD) версию навсегда**: означает несопровождаемую,
  не получающую патчей безопасности зависимость на весь срок жизни проекта — неприемлемо
  для компонента, хранящего сессии и данные rate-limiting/бан-листов.
- **Redis под новой лицензией (RSALv2/SSPLv1)**: юридически совместимо с использованием
  внутри MGate (MGate не перепродаёт Redis как managed service), но создаёт лицензионный
  шум в [`NOTICE`](../../NOTICE) рядом с отдельным решением о правах на сам MGate
  (ADR-0014) — решили не смешивать условия лицензии зависимости с условиями использования
  продукта.
- **KeyDB / Dragonfly** (другие Redis-совместимые форки/реализации): рассматривались,
  но Valkey имеет более широкую индустриальную поддержку (Linux Foundation, AWS, Google,
  Oracle как соучредители) и совпадающий с Redis 7.2 набор команд без дополнительных
  расхождений — выбран как наиболее консервативный (наименее рискованный) вариант замены.
- **Убрать Redis-совместимое хранилище вовсе, использовать только PostgreSQL** (`LISTEN/
  NOTIFY`, unlogged tables для сессий): отклонено — Rspamd требует Redis-совместимый
  backend нативно (`use_redis = true`), а PostgreSQL не заменяет
  требуемую производительность для rate limiting/стрима логов с TTL-семантикой.

## Последствия

- Redis-совместимый клиент бэкенда используется без модификаций — Valkey протокольно
  совместим. Клиент работает с одним endpoint: Redis Cluster и Sentinel не поддерживаются.
- `docker-compose.yml` и вся документация ссылаются на сервис `valkey` (не `redis`) как
  на имя контейнера/хоста; переменная `MGATE_REDIS_URL` продолжает использовать схему
  `redis://` — это осознанное расхождение имени переменной/схемы URL и имени сервиса,
  зафиксированное здесь, чтобы не удивлять новых участников.
- `NOTICE` перечисляет Valkey как BSD-3-Clause зависимость — не требует отдельного
  разбирательства при финализации ADR-0014 (лицензия MGate), в отличие от гипотетического
  включения Redis под RSALv2/SSPLv1.
- Rspamd конфигурируется с `type = redis` (это тип драйвера в конфигурации Rspamd,
  сохранённый исторически проектом Rspamd, а не признак использования Redis как
  продукта) и `servers = "valkey:6379"`, `dbindex` — не совпадает `db 0` (mgate) vs
  `db 1` (rspamd), см. `docs/ARCHITECTURE.md` §2.
