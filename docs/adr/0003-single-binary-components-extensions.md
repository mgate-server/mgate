# 0003. Единый закрытый бэкенд: один бинарник и один образ, роли выбираются подкомандой

Статус: Принято

Дата: 2026-09-12

Связано: ADR [0007](0007-editions-and-licensing-model.md), [0009](0009-repository-split.md),
[0018](0018-spa-public-server-side-enforcement.md); [ARCHITECTURE.md](../ARCHITECTURE.md) §7, §9

## Контекст

Бэкенд MGate — единый сервис, который обслуживает API админ-панели и личного кабинета,
шлюз веб-почты, фоновые задачи (DNS-проверки, ACME, обработку логов, продление лицензии) и
policy-сервис для Postfix. Нужно было решить:

- запускать ли эти роли как отдельные исполняемые файлы или как режимы одного бинарника;
- как Pro-функциональность физически присутствует в поставляемом продукте, чтобы не
  появилось двух расходящихся сборок (Community и Pro) с разным набором исправлений,
  разными тегами и необходимостью менять образ при покупке подписки;
- как это сочетается с тем, что исходный код бэкенда не публикуется, а публичный
  репозиторий содержит только комплект развёртывания, почтовый стек и SPA
  (ADR [0009](0009-repository-split.md)).

## Решение

- Бэкенд — **один закрытый бинарник `mgate`**, распространяемый **одним образом**
  `ghcr.io/mgate-server/mgate`. Роль процесса выбирается подкомандой CLI (`serve`,
  `worker`, `migrate`, `init`, `admin`, `healthcheck`, `openapi`, `license`, `dns`,
  `version`), а для `serve` — списком компонентов `--components` (`api`, `internal`,
  `policy`, `webmail`) в любой комбинации.
- Топология `docker-compose.yml` запускает из этого образа несколько контейнеров с разными
  аргументами: `api` (`serve --components api,internal,policy`), `webmail`
  (`serve --components webmail`), `worker` (`worker`) и одноразовый `migrate`
  (`migrate --bootstrap`). Helm-чарт и all-in-one-образ используют тот же образ и те же
  подкоманды.
- **Сборка бэкенда ровно одна.** Pro-модули присутствуют в образе всегда и включаются только
  действительной лицензией во время работы (ADR [0007](0007-editions-and-licensing-model.md)).
  Редакция Community/Pro — свойство конкретной установки, а не выбор при сборке, не
  отдельный тег и не отдельный образ. Каждый Pro-эндпоинт проверяет права на сервере
  независимо от интерфейса (ADR [0018](0018-spa-public-server-side-enforcement.md)).
- Вспомогательный образ `ghcr.io/mgate-server/mgate-agent` содержит тонкий агент, который
  копируется в почтовые образы (`postfix`, `dovecot`, `rspamd`) при их сборке. Он выпускается
  вместе с `mgate` под той же версией.
- Публичный интерфейс бэкенда — то, что описано в [ARCHITECTURE.md](../ARCHITECTURE.md) §7:
  порты, эндпоинты, переменные окружения, команды CLI, владение данными в PostgreSQL.
  Внутреннее устройство бинарника (модули, способ подключения Pro-функций) публично не
  документируется и может меняться между версиями без предупреждения.

## Альтернативы

- **Отдельные бинарники на роль** (API, веб-почта, фоновые задачи): дублирует инициализацию
  (конфигурация, пулы соединений, миграции, телеметрия) и увеличивает число артефактов,
  которые нужно выпускать и версионировать синхронно. Отклонено.
- **Две сборки — Community и Pro — разными образами или тегами**: переход на Pro потребовал
  бы смены образа и перезапуска, а две сборки неизбежно расходятся по исправлениям. Отклонено:
  один образ, редакция переключается лицензией.
- **Динамическая загрузка Pro-модулей** (разделяемые библиотеки или модули, загружаемые по
  сети после активации): нет стабильного бинарного интерфейса между версиями, загрузка кода
  по сети — дополнительный риск цепочки поставок. Отклонено.
- **Публикация исходного кода базовой части бэкенда с закрытой Pro-надстройкой
  (open-core)**: отклонено продуктовым решением не публиковать исходный код бэкенда вообще
  (ADR [0007](0007-editions-and-licensing-model.md), [0009](0009-repository-split.md)).

## Последствия

- Оператору нужен один образ бэкенда на версию; обновление продукта — смена одного значения
  `MGATE_VERSION`, общего для всех образов (ADR [0009](0009-repository-split.md),
  [DEPLOYMENT.md](../DEPLOYMENT.md) §5).
- Переход на Pro и обратно не требует пересборки, смены образа или перезапуска контейнеров.
- Роли по-прежнему масштабируются независимо: `api`, `webmail` и `worker` — отдельные
  контейнеры одного образа ([ARCHITECTURE.md](../ARCHITECTURE.md) §11, [HA.md](../HA.md)).
- Пересобрать бэкенд из исходников невозможно — исходный код не публикуется. Для разработки
  публичной части используется опубликованный образ; при необходимости он переопределяется
  переменными `MGATE_IMAGE`/`MGATE_AGENT_IMAGE`.
- Этот репозиторий не содержит ни строки кода бэкенда: комплект развёртывания и SPA
  взаимодействуют с ним только через задокументированный интерфейс
  ([ARCHITECTURE.md](../ARCHITECTURE.md) §7) и OpenAPI-спецификацию
  (`web/packages/api-client/openapi.json`, обновляется командой `make openapi-sync` из
  опубликованного образа).
