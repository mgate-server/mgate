# 0016. Сетевая сегментация и внутренняя аутентификация

Статус: Принято

Дата: 2026-09-12

## Контекст

Множество внутренних HTTP/TCP-эндпоинтов (`internal` API на `:8081`, policy delegation
`:10040`/`:12340`, doveadm HTTP API, control API `mgate-agent` на `:7070`, контроллер
Rspamd) не предназначены для внешних клиентов, но физически доступны любому процессу,
способному установить TCP-соединение внутри контейнерной сети — Docker bridge-сети сами
по себе не аутентифицируют отправителя пакета. Нужно решить, как ограничить доступ к
этим эндпоинтам: только сетевой сегментацией, только токенами приложения, или обоими
слоями (defense in depth), и как разделить сети так, чтобы компрометация одного
компонента не давала прямого выхода в интернет.

## Решение

Два слоя защиты одновременно:

1. **Сетевая сегментация**: сеть `backend` — `internal: true` (Docker гарантирует
   отсутствие маршрута наружу для контейнеров, подключённых только к ней); `postgres` и
   `valkey` подключены **только** к `backend` — они физически недостижимы напрямую из
   интернета ни при какой конфигурации Traefik/файрвола хоста. `unbound` имеет
   статический IP в `backend` (`172.30.1.53`) для предсказуемой настройки `dns:` во всех
   остальных сервисах. Сеть `public` — обычный bridge с egress, но входящий доступ извне
   ограничен тем, какие порты явно опубликованы в `docker-compose.yml` (см. `docs/ARCHITECTURE.md` §4) —
   internal-порты (`:8081`, `:10040`, `:7070`, doveadm `:8080` на dovecot, controller
   Rspamd) не публикуются на хост и не проксируются Traefik.
2. **Токен приложения поверх сети** (defense in depth, на случай неправильной настройки
   файрвола хоста, публикации портов пользователем сверх штатной конфигурации, или другого
   контейнера в той же пользовательской docker-сети): каждый вызов `/internal/v1/*` и
   каждый control-вызов `mgate-agent` несёт `Authorization: Bearer
   ${MGATE_INTERNAL_TOKEN}`; doveadm HTTP API использует отдельный `DOVEADM_API_KEY`;
   контроллер Rspamd — `RSPAMD_CONTROLLER_PASSWORD`. Токены — общие секреты в пределах
   инсталляции (не per-request подпись), генерируются `scripts/gen-secrets.sh` при
   `make init`, живут в `.env`, никогда не попадают в образы.

## Альтернативы

- **Только сетевая сегментация, без токенов**: проще, но не защищает от ошибки
  конфигурации (пользователь добавляет свой сервис в сеть `backend`/`public` в
  кастомном compose override, или неправильно настраивает публикацию портов) и от
  compromised-контейнера, который использует внутреннюю сеть для доступа к другим
  внутренним сервисам, если бы у них не было собственной проверки. Отклонено —
  архитектурный принцип проекта: не полагаться на единственный рубеж защиты (тот же
  принцип, что и в лицензировании, см. `docs/LICENSING.md` §13).
- **mTLS между всеми внутренними сервисами**: даёт более сильную гарантию (криптографическая
  аутентификация обеих сторон), но требует полноценного PKI для внутренних сервисов
  (выпуск/ротация внутренних сертификатов для каждого контейнера) — существенно
  увеличивает операционную сложность самостоятельного развёртывания (`docker-compose`
  «из коробки») ради защиты от угрозы (compromised-контейнер внутри `backend`), которая
  уже частично покрыта bearer-токеном и отсутствием egress у `backend`. Отклонено для
  MVP; зафиксировано как возможное усиление (Pro hardening), не блокирует базовую схему.
- **Единый общий секрет для всех внутренних вызовов** (один токен вместо
  `MGATE_INTERNAL_TOKEN`/`DOVEADM_API_KEY`/`RSPAMD_CONTROLLER_PASSWORD` раздельно):
  отклонено — раздельные секреты ограничивают ущерб при компрометации одного из них
  (например, утечка `RSPAMD_CONTROLLER_PASSWORD` через лог не даёт доступа к `mgate`
  internal API).

## Последствия

- Ни один компонент не должен полагаться только на факт «запрос пришёл из сети
  `backend`» как на аутентификацию — проверка токена обязательна в `api`
  (internal-роутер) и `mgate-agent` независимо от сетевой топологии, в которой он
  запущен (это тестируемое требование: тест должен
  проверять отказ без валидного токена).
- Секреты внутренней аутентификации ротируются вручную (regenerate + перезапуск
  сервисов, читающих их); автоматическая ротация — не в объёме этого ADR.
- `firewall`-профиль (`network_mode: host`) — единственный сервис, сознательно
  выходящий за пределы сегментации `public`/`backend` (ему нужен доступ к сетевому
  стеку хоста для управления nftables) — компенсируется минимальным образом (только
  nftables + `mgate-agent --role firewall`) и `cap_add: [NET_ADMIN, NET_RAW]` вместо
  привилегированного режима.
- Подробный анализ угроз каждого внутреннего канала (что происходит при утечке каждого
  токена, какие данные защищает каждый слой) — `docs/SECURITY.md`, не дублируется здесь.
