# 0011. Веб-почта: собственный Rust IMAP-шлюз вместо SSO в Snappymail

Статус: Принято (дополнено 2026-09-12 — шлюз `webmail`
входит в закрытый образ бэкенда, UI отдаётся отдельным публичным образом `web`;
см. «Дополнение» ниже)

Дата: 2026-09-12

## Дополнение (2026-09-12)

Шлюз `webmail` (упомянутый ниже как «Rust-сервис») входит в закрытый образ бэкенда
`ghcr.io/mgate-server/mgate` — его исходный код не публикуется, только
поведение контейнера `webmail` (порт 8082, документировано в `docs/ARCHITECTURE.md`
§2 и §4). Само решение (собственный шлюз вместо SSO в стороннем PHP-клиенте) не
изменилось. Дополнительно: UI веб-почты (`/mail/*`) отдаётся отдельным публичным
образом `web` (nginx, `docker/web/`, ADR-0012), не самим бэкендом — это уточнение
касается ADR-0012, но упомянуто здесь, так как оба ADR описывают один и тот же UI.

## Контекст

Нужно было выбрать: собственная веб-почта поверх IMAP/SMTP с REST/WebSocket-API или
интеграция готового клиента Snappymail через SSO. Snappymail (PHP) — зрелый, готовый веб-клиент, интеграция которого через SSO
(создание временной сессии/токена, встраивание в iframe или редирект) существенно
ускорила бы получение работающей веб-почты, но:

- добавляет PHP как ещё один язык выполнения в стек (только ради одного компонента),
  требующий отдельного контейнера, отдельной модели обновлений безопасности;
- ограничивает глубину интеграции с остальной SPA (единый вид, общая навигация между
  `/admin`, `/account`, `/mail` и общая точка расширения для Pro-страниц, ADR-0012)
  — Snappymail как отдельное веб-приложение в iframe плохо сочетается с общей шапкой/
  переключением между разделами и с единым API-клиентом, сгенерированным из OpenAPI;
  а без общего API-клиента разошлись бы конвенции аутентификации, CSRF и т.п. между
  «нашим» API и SSO-сессией Snappymail;
- не даёт единообразного индикатора SPF/DKIM входящего письма, блокировки трекеров
  и т. п. без патчей стороннего PHP-приложения — что вновь означало бы
  форк/патчинг чужого кода, а не написание собственного.

## Решение

Собственный шлюз веб-почты — сервис **`webmail`** (написан на Rust, исполняется отдельным
контейнером, слушает `:8082`): пул IMAP-соединений на пользовательскую сессию, разбор и
санитайзинг MIME/HTML (`mail-parser`, `ammonia`), блокировка внешних изображений по
умолчанию, отправка через SMTP submission (`lettre`), поиск, вложения, контакты,
WS-пуш через IMAP IDLE. UI веб-почты — часть единой React SPA (`/mail/*`, ADR-0012), а
не отдельное приложение.

## Альтернативы

- **SnappyMail через SSO** (описано выше) — отклонён по причинам интеграции и
  дополнительного языка выполнения; остаётся зафиксированным как рассмотренная
  альтернатива: если собственная веб-почта не оправдает себя, к этому варианту можно
  вернуться (потребует нового ADR, заменяющего этот).
- **Roundcube** (другой зрелый PHP-веб-клиент): те же аргументы против, что и для
  Snappymail.
- **JMAP вместо IMAP как протокол шлюза** (например, поверх Stalwart): не выбрано, так
  как основной почтовый стек — Dovecot (ADR-0002), который в первую очередь IMAP-сервер;
  JMAP-прокси поверх IMAP добавил бы транспортный слой без выигрыша на этом этапе.

## Последствия

- Шлюз `webmail` должен поддерживать IMAP IDLE и держать пул соединений по одному (или
  несколько) на активную пользовательскую сессию — это стейтфул-компонент (в отличие от
  `api`/`worker`), что ограничивает его горизонтальное масштабирование session affinity
  требованиями (см. `docs/ARCHITECTURE.md` §11, открытый вопрос).
- Вся обработка недоверенного HTML писем (наиболее чувствительная к XSS часть системы)
  сосредоточена в одном сервисе (`webmail`, санитайзер `ammonia`) — это одновременно и
  сужает поверхность атаки до одного места аудита, и делает его критичным компонентом
  для `docs/SECURITY.md` (STRIDE: Tampering/Information Disclosure через XSS).
- Объём работы над веб-почтой существенно больше, чем при SSO-интеграции —
  осознанно принятая стоимость ради единообразия продукта и отсутствия PHP в стеке.
- Функциональность веб-почты (индикатор SPF/DKIM, блокировка трекеров, WYSIWYG-редактор,
  контакты/vCard) реализуется как часть шлюза `webmail` + `web/apps/spa`, без внешних
  зависимостей на чужой веб-клиент.
