# 0004. Аутентификация делегирована API (passdb) + SQL userdb + app passwords для 2FA-пользователей

Статус: Принято (решение); проверка TOTP при входе — **в разработке**: в текущей версии вход выполняется только по паролю (пароли приложений работают), см. [SECURITY.md](../SECURITY.md) §8

Дата: 2026-09-12

## Контекст

Dovecot и Postfix (через Dovecot SASL) должны проверять пароли пользователей почты.
Продуктовые требования: Argon2id (либо SHA-512-crypt при импорте), TOTP-based
2FA, а в перспективе — единую политику брутфорс-защиты и журнал входов, видимые в
админ-панели. Dovecot умеет проверять пароли напрямую по SQL (`passdb sql`), что было бы
проще, но:

- Argon2id-проверка "из коробки" в Dovecot ограничена его собственной реализацией и
  версией схемы хранения; TOTP/2FA и одноразовые app-пароли для клиентов без поддержки
  TOTP не являются частью стандартного `passdb sql`;
- единая точка бан-листов/rate-limit (Valkey) нужна и для IMAP, и для SMTP submission —
  дублировать эту логику в двух местах (Dovecot Lua-скрипт и отдельно в Postfix policy)
  рискованно с точки зрения рассинхронизации;
- журнал входов (`login_events`) должен фиксироваться в единообразном формате для показа
  в Live Logs/истории входов пользователя, независимо от протокола (IMAP/POP3/SMTP AUTH).

## Решение

Проверка пароля (passdb) для Dovecot **делегирована HTTP-вызовом в `mgate` API**:
`POST http://api:8081/internal/v1/dovecot/passdb` — единственное место, где реализованы
Argon2id-проверка, проверка app-паролей (для пользователей с включённым 2FA), запись в
`login_events`, применение бан-листов. Механизм вызова на стороне Dovecot — Lua passdb
(HTTP-клиент Dovecot 2.4) либо `checkpassword`-драйвер, вызывающий `mgate-agent
checkpassword`; конкретный выбор описан в `docs/mail/dovecot.md` и не меняет
контракт HTTP-эндпоинта.
Отдельно, **userdb (какой uid/gid/home/quota) читается Dovecot напрямую из PostgreSQL**
через представление `v_dovecot_userdb` (роль `mgate_mail`, SELECT-only) — так LMTP-
доставка новой почты не зависит от доступности `api` (см. §12 «Режимы отказа» в
`docs/ARCHITECTURE.md`). Аналогично для Postfix submission: SASL идёт через
`smtpd_sasl_path = inet:dovecot:12345`, то есть тем же путём Dovecot → API passdb —
Postfix не обращается к API напрямую за паролями. Дополнительно — auth-policy (rate
limit/бан на уровне попытки логина, до проверки пароля) через `auth_policy_server_url =
http://api:8081/internal/v1/dovecot/policy`.

## Альтернативы

- **`passdb sql` напрямую в Dovecot** (без API): проще технически, но не даёт единой
  точки для Argon2id с нужными параметрами, app-паролей 2FA-пользователей и общего
  журнала попыток входа со всех протоколов; потребовало бы дублирования rate-limit
  логики между Dovecot (Lua) и Postfix policy-сервисом. Отклонено из-за риска
  рассинхронизации политики между IMAP и SMTP.
- **Полностью свой IMAP/SMTP auth-сервер вместо Dovecot passdb hook**: избыточно, Dovecot
  уже предоставляет расширяемые точки интеграции (Lua passdb, checkpassword,
  auth-policy) — нет причин их не использовать.
- **userdb тоже через API** (единая точка для passdb и userdb): отклонено — сделало бы
  каждую LMTP-доставку зависимой от доступности `api`, что нарушает принцип
  «доставка почты не должна падать вместе с UI/API» (см. §12 `docs/ARCHITECTURE.md`).

## Последствия

- Бэкенд — единственное место, где реализованы Argon2id-параметры, генерация/
  проверка TOTP и app-паролей, и одна и та же реализация используется и для входа в SPA, и
  во внутреннем passdb-эндпоинте — один набор параметров хэширования.
- Отказ `api` временно блокирует новые IMAP/SMTP-логины (см. таблицу отказов в
  `docs/ARCHITECTURE.md` §12), но не блокирует доставку почты и не обрывает уже открытые
  IMAP-сессии — осознанный компромисс, а не побочный эффект.
- Внутренний эндпоинт защищён `Authorization: Bearer ${MGATE_INTERNAL_TOKEN}` и не
  проксируется Traefik наружу (см. `docs/ARCHITECTURE.md` §3) — подробности угроз этого канала
  см. `docs/SECURITY.md`.
- Выбор между Lua passdb и `checkpassword` не влияет на контракт HTTP-эндпоинта
  (`/internal/v1/dovecot/passdb`, JSON-запрос/ответ): он стабилен независимо от того,
  какой из двух механизмов вызовет его на стороне Dovecot; финальный выбор
  задокументирован в `docs/mail/dovecot.md`.
