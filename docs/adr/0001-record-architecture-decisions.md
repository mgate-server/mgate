# 0001. Фиксировать архитектурные решения через ADR

Статус: Принято

Дата: 2026-09-12

## Контекст

Проект MGate разрабатывается параллельно несколькими независимыми командами и
контрибьюторами, каждый из которых отвечает за свою область кода/документации. Решения, которые
затрагивают более одной области (выбор технологии почтового стека, схема аутентификации,
разбиение на репозитории и т. п.), должны быть зафиксированы так, чтобы:

- новый участник мог быстро понять «почему так», не читая историю чатов/коммитов;
- решение можно было пересмотреть осознанно (через новый ADR, который заменяет старый),
  а не молча продублировать в трёх разных README с расхождениями;
- `docs/ARCHITECTURE.md` и `docs/CONFIGURATION.md` оставались краткими нормативными
  документами (имена/порты/API/переменные), а обоснования жили отдельно и не раздували их.

## Решение

Использовать Architecture Decision Records (ADR) в формате Майкла Найгарда, по одному
файлу на решение, в `docs/adr/NNNN-kebab-case-title.md`, по шаблону
`docs/adr/0000-template.md` (Статус, Контекст, Решение, Альтернативы, Последствия).
Нумерация сквозная, не переиспользуется даже для устаревших/отклонённых решений.
Если решение меняется — создаётся новый ADR со статусом «Принято», а старый получает
статус «Заменено ADR-XXXX» (файл не удаляется — история решений ценна сама по себе).
За каждый ADR отвечает мейнтейнер соответствующей области.

## Альтернативы

- **Только `docs/ARCHITECTURE.md`**: документ и так растёт; смешивание нормативных
  фактов («порт 8081») с обоснованиями («почему не Exim») сделало бы его нечитаемым и
  затруднило бы поиск single source of truth для конкретного порта/имени.
- **Обоснования в README каждого репозитория/крейта**: решения, затрагивающие несколько
  репозиториев (например, выбор Valkey влияет и на `mgate` и на конфигурацию Rspamd),
  расползлись бы по нескольким файлам без единого места для ссылки.
- **Не документировать вовсе, полагаться на комментарии в коде**: не работает для решений
  на уровне инфраструктуры/репозиториев, которые не привязаны к конкретному файлу кода.

## Последствия

Каждое значимое кросс-областное решение с этого момента обязано иметь ADR-файл в
`docs/adr/`; `docs/ARCHITECTURE.md` и `docs/CONFIGURATION.md` ссылаются на конкретные номера
вместо повторения обоснования. Стоимость: лишний файл на каждое решение, дисциплина
поддержания статуса актуальным. Это принято сознательно как более дешёвый вариант, чем
устные/чатовые обоснования, теряющиеся со временем.
