# 0002. Почтовый стек: Postfix + Dovecot 2.4 + Rspamd

Статус: Принято

Дата: 2026-09-12

## Контекст

В качестве MTA рассматривались варианты «Haraka / Postfix / Exim», для
IMAP/POP3/Sieve — Dovecot, для антиспама — Rspamd. Нужно выбрать один MTA и
зафиксировать это как обязательный для всех компонентов почтового стека выбор, а не
оставлять как открытый вопрос, потому что от него зависят: схема виртуальных доменов
через PostgreSQL (`v_postfix_*`), протокол взаимодействия с Rspamd (milter), схема SASL
через Dovecot, структура Docker-образов (`docker/postfix/`, `docker/dovecot/`,
`docker/rspamd/`).

Дополнительно рассматривался Stalwart Mail Server — современный all-in-one сервер на
Rust (SMTP+IMAP+JMAP в одном процессе), потенциально привлекательный тем, что сам
написан на том же языке, что и `mgate`.

## Решение

Использовать связку **Postfix (MTA) + Dovecot 2.4 (IMAP/POP3/LMTP/ManageSieve) +
Rspamd (антиспам, DKIM/ARC-подпись, SPF/DMARC) + ClamAV (антивирус, через `clamd`)**,
как описано в `docs/ARCHITECTURE.md` (§1–§2). Каждый компонент — отдельный,
общепризнанный проект с многолетней эксплуатационной репутацией на production-нагрузках,
интегрируемый через задокументированные протоколы (milter, LMTP, SASL, SQL-таблицы), а
не через недокументированные внутренние API.

## Альтернативы

- **Haraka** (Node.js MTA): гибкая плагинная архитектура, но существенно меньшая
  эксплуатационная база на высоконагруженных инсталляциях по сравнению с Postfix;
  добавление ещё одного языка выполнения (Node.js в почтовом ядре, а не только во
  фронтенде) увеличивает поверхность сопровождения без выигрыша в возможностях, которые
  нужны продукту.
- **Exim**: сопоставим с Postfix по зрелости, но менее распространён в контейнерных
  дистрибутивах и имеет более сложный, менее декларативный конфигурационный язык
  (Exim string expansions против Postfix `main.cf`/`master.cf` + `pgsql:`-карт), что
  усложнило бы генерацию конфигурации из шаблонов.
- **Stalwart Mail Server** (Rust, all-in-one SMTP+IMAP+JMAP): привлекателен единым языком
  и современной архитектурой, но на момент решения (2026) существенно менее обкатан в
  продакшене под целевой нагрузкой (50 сообщений/с, произвольные MUA), не имеет
  такой же экосистемы milter-совместимых антиспам-фильтров, и его использование лишило бы
  проект возможности использовать Rspamd как отдельный, независимо развиваемый компонент.
  Открытый вопрос на будущее (не блокирует текущую архитектуру): при существенном созревании Stalwart
  можно рассмотреть его как альтернативный backend за тем же набором внешних протоколов
  (IMAP/SMTP), не меняя API `mgate` — предмет отдельного ADR, если возникнет.
- **Полностью самописный MTA/IMAP на Rust**: избыточный риск и объём работы; использование готовых
  компонентов ("Haraka / Postfix / Exim" как варианты) вполне допустимо.

## Последствия

- Docker-образы `docker/postfix/`, `docker/dovecot/`, `docker/rspamd/`, `docker/clamav/`
  строятся вокруг Debian trixie-slim пакетов этих проектов (версии пинуются в
  Dockerfile соответствующих образов).
- Интеграция MGate с почтовым ядром идёт исключительно через задокументированные внешние
  протоколы (SQL-представления `v_postfix_*`/`v_dovecot_userdb`, milter на `:11332`,
  LMTP на `:24`, SASL на `:12345`, policy delegation на `:10040`/`:12340`) — не через
  патчи исходного кода Postfix/Dovecot/Rspamd. Это позволяет обновлять версии этих
  компонентов независимо от версии `mgate`.
- Каждый компонент имеет собственную лицензию (см. [`NOTICE`](../../NOTICE)); это учтено
  при выборе модели лицензирования публичного репозитория (ADR-0014) —
  в частности, ClamAV (GPL-2.0) интегрирован только по сети (`clamd`), без статической/
  динамической линковки, что задокументировано в `NOTICE`.
- Дальнейшие детали конфигурации каждого демона — `docs/mail/{postfix,dovecot,rspamd}.md`.
