# Высокая доступность и масштабирование MGate (HA Architecture)

> **Статус и область применения**: Данный документ содержит архитектурные рекомендации, сценарии отказоустойчивости и руководство по развёртыванию компонентов MGate в отказоустойчивой конфигурации.
>
> **Честное ограничение архитектуры**: В текущих версиях (CalVer `YYYY.M.N`) проект **не заявляет** поддержку распределённого режима Active-Active для очередей Postfix со сквозной синхронизацией локального спула. Полноценная кластеризация строится по схеме горизонтального масштабирования stateless-сервисов (API, Webmail, Rspamd, Ingress Postfix) и отказоустойчивой изоляции stateful-хранилищ (один активный Dovecot на хранилище `vmail` с холодным/горячим резервом, общая ФС, реплицированный PostgreSQL, один endpoint Valkey/Redis).

## 2. Три ключевых сценария отказа и их митигация

### Сценарий 1: Отказ узла Postfix (Ingress / Egress MTA)

* **Характер сбоя**: Аппаратный сбой сервера, падение гипервизора, сетевая изоляция или сбой процесса Postfix на одной из нод входящей почты.
* **Влияние на входящий трафик**:
  - Внешние отправляющие почтовые серверы (MTA) распределяют нагрузку между несколькими записями MX с одинаковым приоритетом (`MX 10 mail1.example.com`, `MX 10 mail2.example.com`) либо через L4-балансировщик с healthcheck по порту 25.
  - При недоступности упавшего узла отправляющий MTA согласно стандарту **RFC 5321** автоматически выбирает другой доступный MX-сервер либо удерживает сообщение в локальной очереди и повторяет попытки в течение 4–5 суток.
* **Влияние на исходящий трафик и локальный спул**:
  - Каждая нода Postfix имеет **собственный независимый spool** (`/var/spool/postfix`). Расшаривание директории спула между несколькими экземплярами Postfix категорически запрещено во избежание гонок блокировок `master.lock` и повреждения структуры очередей.
  - Сообщения, принятые отказавшей нодой и не успевшие доставиться, остаются в её локальном спуле до восстановления ноды.
* **Рекомендуемая митигация**:
  1. Публикация минимум двух географически разнесённых MX-записей в DNS.
  2. Использование внешнего L4 балансировщика (Keepalived / VRRP / AWS NLB) для входящих SMTP-подключений с проверкой `TCP/25` и баннера ESMTP каждые 3 секунды.
  3. Для планового обслуживания узла: перевод ноды в режим drain (`postqueue -f`, отключение входящего порта в балансировщике, ожидание опустошения локальной очереди `postqueue -p`).

### Сценарий 2: Отказ узла Dovecot (active/passive)

> **Dovecot Director не используется.** В Dovecot 2.4 Community Edition (версия, поставляемая в образе `dovecot`) Director удалён, поэтому балансировка пользователей по нескольким работающим одновременно узлам Dovecot **не поддерживается**. Поддерживаемая схема — **active/passive: один работающий экземпляр Dovecot на одно хранилище `vmail`**.

* **Характер сбоя**: падение узла Dovecot, который обслуживает IMAP/POP3 и принимает доставку по LMTP от Postfix.
* **Почему нельзя запускать несколько активных Dovecot на одном `vmail`**:
  - Формат Maildir безопасен для параллельной записи новых писем разными процессами (уникальные имена файлов в `tmp/` с атомарным `rename` в `new/`).
  - Однако индексные файлы (`dovecot.index`, `dovecot.index.cache`) и список UID (`dovecot-uidlist`) требуют синхронизации. Если два экземпляра Dovecot одновременно изменяют один ящик без координации (а Director, который направлял бы пользователя всегда на один узел, недоступен), возможны сброс блокировок и рассинхронизация счётчиков.
* **Рекомендуемая митигация**:
  1. **Active/passive**: один активный Dovecot; резервный экземпляр на другом узле запускается только после того, как активный гарантированно остановлен (fencing: отключение от сети/хранилища, STONITH). Переключение виртуального IP или DNS-имени Dovecot выполняется средствами инфраструктуры (Keepalived / VRRP, Pacemaker, оркестратор). В Kubernetes это StatefulSet с одной репликой `dovecot`, которая переезжает на другой узел вместе с томом.
  2. **Блокировки для сетевых ФС** (при `vmail` на NFSv4 / JuiceFS) в `dovecot.conf`:
     ```dovecot
     mmap_disable = yes
     mail_fsync = optimized
     lock_method = dotlock
     ```
     Это гарантирует корректность работы индексов Dovecot поверх сетевых ФС.
  3. **Таймауты LMTP в Postfix**: пока Dovecot недоступен, Postfix удерживает письма в очереди и повторяет доставку; при необходимости настройте очереди:
     ```postfix
     lmtp_destination_concurrency_limit = 20
     lmtp_destination_recipient_limit = 1
     lmtp_connect_timeout = 10s
     ```

### Сценарий 3: Сетевое расщепление (Split-Brain) распределённого хранилища

* **Характер сбоя**: Нарушение сетевой связности между нодами почтового сервера и централизованной системой хранения (NFS / JuiceFS / CephFS), либо изоляция мастера базы данных PostgreSQL.
* **Последствия без защиты**:
  - Узел, потерявший связь с хранилищем, может возвращать ошибки `Mailbox unavailable / 451 Temporary local problem`.
  - При наличии нескольких реплик хранилища разорванные сегменты сети могут начать независимо принимать изменения, что приводит к необратимому расхождению истории Maildir и транзакций PostgreSQL.
* **Рекомендуемая митигация**:
  1. **Строгий кворум метаданных (Quorum / Fencing)**:
     - Для JuiceFS: использование отказоустойчивого движка метаданных (например, etcd, TiKV или PostgreSQL) с обязательным кворумом (Raft: не менее 3 или 5 нод). При потере кворума узел монтирования немедленно блокирует операции записи в режим read-only.
     - Для NFS: использование NFSv4 с параметрами монтирования `hard,intr` (запрет `soft`-монтирования, которое при таймаутах возвращает ошибку ввода-вывода и может повредить целостность Maildir).
  2. **Fail-Closed политика PostgreSQL (Patroni)**:
     - Использование Patroni с etcd / Consul для автоматического переключения мастера (failover).
     - Механизм watchdog / fencing (STONITH) исключает существование двух мастеров одновременно.
  3. **Поведение почтового ядра при потере хранилища**:
     - При недоступности `/var/vmail` Dovecot LMTP возвращает Postfix временную ошибку `450/451 Temporary failure`.
     - Postfix удерживает письма в очереди и повторяет попытку согласно расписанию `queue_run_delay`, предотвращая потерю клиентской корреспонденции.

## 3. Интеграция с внешними базами данных

### 3.1 Внешний PostgreSQL
Для подключения внешнего отказоустойчивого кластера PostgreSQL (AWS RDS Multi-AZ, Cloud Native PostgreSQL, Patroni):
1. Отключите локальный StatefulSet в Helm:
   ```yaml
   postgresql:
     enabled: false
   externalDatabase:
     host: "postgres-ha.internal"
     port: 5432
     database: "mgate"
     username: "mgate"
     existingSecret: "mgate-postgres-credentials"
     existingSecretPasswordKey: "password"
   ```
2. Убедитесь в наличии прав на создание схем и таблиц для пользователя `mgate`, а также в доступности расширений `pgcrypto` и `uuid-ossp`.

### 3.2 Внешний Valkey / Redis
MGate использует Redis-совместимое хранилище для:
- Сессий пользователей (db 0).
- Лимитов частоты запросов policy-сервиса (db 0).
- Кэша и метаданных спам-фильтра Rspamd (db 1).

**Требуется одна точка подключения.** `MGATE_REDIS_URL` (в Helm — `externalValkey`) должен указывать на **единый endpoint**: отдельный экземпляр Valkey/Redis либо управляемый сервис с фиксированным адресом primary (репликация и failover на стороне сервиса допустимы, пока клиент подключается к одному и тому же адресу). **Redis Cluster и Sentinel не поддерживаются**: бэкенд не выполняет маршрутизацию по слотам кластера (запросы к узлам кластера получат ответы `MOVED`) и не умеет обнаруживать мастер через Sentinel; hash-теги в ключах не используются.

```yaml
valkey:
  enabled: false
externalValkey:
  host: "valkey.internal"       # один endpoint
  port: 6379
  existingSecret: "mgate-valkey-credentials"
```

## 4. Сетевые файловые системы для `/var/vmail`

### 4.1 NFS v4
* **Рекомендуемая версия**: NFSv4.1 или NFSv4.2 (улучшенная обработка блокировок и обхода сбоев сервера).
* **Опции монтирования в `/etc/fstab` или StorageClass**:
  ```
  rw,noatime,nodiratime,hard,intr,rsize=1048576,wsize=1048576,nfsvers=4.1,tcp,lock,actimeo=1
  ```
  * `noatime,nodiratime` — исключает лишние операции записи метаданных при чтении писем.
  * `hard,intr` — гарантирует завершение операций записи при кратковременных сетевых задержках без повреждения данных.
  * `actimeo=1` — снижает время кэширования атрибутов файлов до 1 секунды для своевременной синхронизации списка писем между серверами.

### 4.2 JuiceFS поверх S3
* JuiceFS предоставляет POSIX-совместимую файловую систему с хранением блоков данных в любом S3-совместимом объектном хранилище (MinIO, AWS S3, Ceph RGW) и хранением метаданных в Redis/PostgreSQL.
* **Преимущества для почтового кластера**:
  - Неограниченный масштаб хранилища писем без необходимости ручного расширения LUN/дисков.
  - Локальный кэш на быстрых NVMe-дисках нод ускоряет операции чтения частых писем и индексов.
  - Встроенное сжатие (Zstandard/LZ4) снижает расходы на хранилище.
* **Пример конфигурации монтирования JuiceFS**:
  ```sh
  juicefs mount \
    --cache-dir=/var/jfsCache \
    --cache-size=20480 \
    --free-space-ratio=0.1 \
    --writeback \
    redis://valkey-meta.internal:6379/2 \
    /var/vmail
  ```

## 5. Итоговый чек-лист отказоустойчивости перед запуском в прод

- [ ] В DNS настроено не менее двух равнозначных записей MX на независимые IP-адреса.
- [ ] Очереди Postfix изолированы (каждый узел пишет только в собственный локальный `/var/spool/postfix`).
- [ ] Dovecot работает по схеме Active-Passive: **один** активный экземпляр на хранилище `/var/vmail`, резервный запускается только после fencing активного (Director в Dovecot 2.4 CE отсутствует).
- [ ] Сетевая ФС `/var/vmail` протестирована на поведение при сетевых таймаутах (режим `hard`).
- [ ] PostgreSQL развёрнут с механизмом автоматического failover (Patroni / PGO) и подтверждённым RPO/RTO.
- [ ] Valkey/Redis доступен по одному стабильному endpoint (репликация/failover — на стороне сервиса); Redis Cluster и Sentinel не используются.
