# Участие в разработке MGate

Спасибо за интерес к проекту. Этот репозиторий публикует deploy kit, конфигурацию
почтового стека и исходный код SPA платформы MGate. Права на использование,
изменение и распространение определяются [`LICENSE`](LICENSE) и
[`EULA.md`](EULA.md). Закрытый backend в репозиторий не входит и принимать
изменения в него через GitHub нельзя.

## Как устроен процесс

GitHub-репозиторий [mgate-server/mgate](https://github.com/mgate-server/mgate) —
**зеркало релизов**, а не место основной разработки:

1. Основная разработка ведётся во внутреннем дереве вендора.
2. Каждый релиз публикуется на GitHub одним снимком-коммитом (без истории) вместе
   с [GitHub Release](https://github.com/mgate-server/mgate/releases).
3. **Issues и pull request'ы на GitHub приветствуются.** Мейнтейнеры рассматривают
   pull request, и принятые изменения **переносятся вручную в основное дерево
   разработки**. В репозитории на GitHub они появляются со следующим релизом.
4. Автор переноса указывается в сообщении коммита через `Co-authored-by`, так что вклад
   сохраняется в истории проекта. После переноса pull request закрывается с
   комментарием, в какой версии ожидается изменение.

Поэтому pull request не будет «влит» в `main` кнопкой Merge, и между принятием
и релизом проходит время — это ожидаемое поведение, а не потерянный запрос.

## Что принимается

- исправления ошибок в конфигурации почтового стека, compose-файлах, Helm-чарте,
  скриптах и SPA;
- улучшения и исправления документации (русский язык в прозе, английский — в коде,
  комментариях и идентификаторах);
- тесты и инструменты проверки.

Крупные изменения (новые компоненты, смена архитектуры, новые зависимости)
сначала обсудите в issue, чтобы не тратить время на работу, которую нельзя будет
принять.

## Как подготовить pull request

- Один pull request — одна тема; небольшой и понятный diff рассматривается быстрее.
- Сообщения коммитов — [Conventional Commits](https://www.conventionalcommits.org/)
  (`feat(web): ...`, `fix(postfix): ...`, `docs: ...`); тип, область и краткое описание — на английском.
- Для изменений SPA: `make typecheck-web lint-web test-web build-web`.
- Для изменений конфигурации и образов: `make validate-configs` и `make compose-config`.
- Незавершённую работу помечайте `TODO(S<N>): <что именно осталось>` (`N` — стадия из [`docs/ROADMAP.md`](docs/ROADMAP.md)), а не голым `TODO`.
- Не добавляйте секреты: в `.env.example` только пустые значения и плейсхолдеры.
- Обновляйте документацию в `docs/` (и `README.md`), если меняется видимое
  поведение или порядок эксплуатации.
- Не меняйте номера версий вручную (`VERSION`, `Chart.yaml`, `package.json`,
  `MGATE_VERSION` в `.env.example`) — их проставляет релизный конвейер.

## Issues и вопросы

- **Баги и некорректное поведение** — заведите issue: что ожидалось и что произошло,
  версия (`MGATE_VERSION` или файл `VERSION`), минимальный пример воспроизведения.
- **Вопросы по эксплуатации и конфигурации** — issue с шаблоном вопроса.
- **Уязвимости безопасности** — **не** через публичные issues, см.
  [`SECURITY.md`](SECURITY.md).
